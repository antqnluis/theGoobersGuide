## Overview and objectives

M3 gives each character an inventory and a coin purse. Both are part of the character's sheet, so they are private by default and shared exactly when the sheet is shared. Both are built for use at the table: adding an arrow, spending gold, or equipping a sword saves immediately, without opening the sheet editor.

M3 delivers:

1. **Five currency columns on `public.character_sheets`** (`cp`, `sp`, `ep`, `gp`, `pp`), never negative. They are written only through an atomic delta RPC, so spending from two devices never loses an update.
2. **A `public.character_items` table** with RLS that mirrors the sheet: the owner always, other current members only when the sheet is shared. It has explicit grants, a 200-item cap per character, and a `character_id` that never changes.
3. **Two RPCs** for changes that must be atomic: `adjust_character_currency` and `adjust_character_item_quantity`.
4. **Coins and Inventory sections in `CharacterSheet`**: balances, add and spend, an item list with quick quantity and equip controls, add, edit, and delete item forms, and derived totals (coin value, carried weight against carrying capacity). Shared sheets show both sections read-only, including from the Party panel.
5. **Updated copy** for deleting a character and deleting a campaign, because both now remove inventories and coins.
6. **Tests**: multi-account integration tests against the local stack (including attempts to bypass the frontend and concurrent deltas), unit tests, and mocked and real-stack browser tests.

## 2. Database schema, constraints, and relationships

### 2.1 Currency columns on `public.character_sheets` (D2, D3)

```sql
alter table public.character_sheets
  add column cp integer not null default 0,
  add column sp integer not null default 0,
  add column ep integer not null default 0,
  add column gp integer not null default 0,
  add column pp integer not null default 0,
  add constraint character_sheets_currency_check check (
    cp between 0 and 9999999 and sp between 0 and 9999999 and ep between 0 and 9999999
    and gp between 0 and 9999999 and pp between 0 and 9999999
  );
```

- A constant default means PostgreSQL adds the columns without rewriting the table. The check validates the existing row (all zeros).
- No update grant is added, so clients cannot set balances directly. `adjust_character_currency` is the only client write path (§4.2).
- The existing table-level `select` grant and the read policy expose the columns to exactly the people who can read the sheet (D1).

### 2.2 `public.character_items`

```sql
create table public.character_items (
  id uuid primary key default gen_random_uuid(),
  character_id uuid not null references public.characters (id) on delete cascade,
  name text not null,
  quantity integer not null default 1,
  weight numeric(7, 2),
  description text,
  equipped boolean not null default false,
  attuned boolean not null default false,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),

  constraint character_items_name_check check (
    name = btrim(name) and char_length(name) between 1 and 80 and name !~ '[[:cntrl:]]'
  ),
  constraint character_items_quantity_check check (quantity between 0 and 9999),
  constraint character_items_weight_check check (weight is null or weight between 0 and 99999.99),
  -- Newlines and tabs are allowed in descriptions; other control characters are not.
  constraint character_items_description_check check (
    description is null
    or (char_length(description) between 1 and 2000
        and description !~ '[\x01-\x08\x0B\x0C\x0E-\x1F\x7F]')
  )
);

create index character_items_character_id_idx on public.character_items (character_id);
```

Notes:

- The table has no `campaign_id` or `owner_id`. Both come from the character, which can never move (B2), so copying them here would add drift risk without adding integrity.
- Empty `description` and `weight` are stored as `null`. The client normalizes `''` to `null`.
- `numeric(7, 2)` holds fractional weights (0.25 lb) exactly.

### 2.3 Guard trigger (every write path)

```sql
create function private.guard_character_item_write()
returns trigger
language plpgsql
security definer set search_path = ''
as $$
begin
  if tg_op = 'UPDATE' then
    if new.id <> old.id or new.character_id <> old.character_id then
      raise integrity_constraint_violation using message = 'item_reassignment_forbidden';
    end if;
    return new;
  end if;

  -- INSERT: serialize inserts for one character, then enforce the cap (D6).
  perform 1 from public.characters where id = new.character_id for no key update;
  if (select count(*) from public.character_items where character_id = new.character_id) >= 200 then
    raise exception 'item_limit_reached';
  end if;
  return new;
end;
$$;

revoke all on function private.guard_character_item_write()
  from public, anon, authenticated, service_role;

create trigger character_items_guard_write
  before insert or update on public.character_items
  for each row execute function private.guard_character_item_write();

create trigger character_items_set_updated_at
  before update on public.character_items
  for each row execute function private.set_updated_at();
```

- The trigger is SECURITY DEFINER, so the count sees every row whatever the caller's RLS. It also applies to `postgres` and `service_role` writes, such as a future M8 import.
- `for no key update` on the character row serializes concurrent inserts for the same character, so the cap holds under concurrency. It does not conflict with the FK's `for key share`. It does conflict with the character RPCs' `for update`, which is harmless because both are short. Lock order stays `characters` → `character_items`, and no M3 path locks an item and then a character, so the two cannot deadlock.
- `characters_guard_write` and `character_items_guard_write` both fire `before`. Their order does not matter.

### 2.4 Relationships and delete behaviour

| Event | Effect |
| --- | --- |
| Campaign deleted | Characters cascade, then sheets (with coins) and items. |
| Character deleted by its owner | Sheet (with coins) and items cascade. |
| Member's account hard-deleted | Their characters cascade, taking their items and coins with them. |
| Leave or removal | Everything is kept. Reads and writes stop through RLS (§3). |
| Rejoin | The same rows are readable and writable again. |
| Ownership transfer | No effect. |

characters 1 ──┬── 1 character_sheets (vitals, body, cp…pp)
               └──< character_items

## 3. RLS policies and authorization matrix

### 3.1 Grants

```sql
alter table public.character_items enable row level security;

revoke all on table public.character_items from public, anon, authenticated, service_role;

grant select, delete on table public.character_items to authenticated;
grant insert (character_id, name, quantity, weight, description, equipped, attuned)
  on table public.character_items to authenticated;
grant update (name, quantity, weight, description, equipped, attuned)
  on table public.character_items to authenticated;
```

- `id`, `created_at`, and `updated_at` are not insertable. `character_id` is insertable but not updatable.
- Items use direct writes: each touches one row, needs no serialization with membership beyond what RLS gives, and is fully covered by the policies, the checks, and the guard (the same reasoning as sheet writes in M03.2 §5.4). Only quantity deltas need an RPC (§4.3).
- `character_sheets` grants are unchanged. The new currency columns get no update grant.

### 3.2 Policies

```sql
-- Read: the owner always; other current members only when the sheet is shared (D1).
-- The subquery is filtered by the characters SELECT policy (membership of both sides).
create policy "Owners and shared members read items"
  on public.character_items for select to authenticated
  using (
    exists (
      select 1 from public.characters as c
      where c.id = character_items.character_id
        and (c.owner_id = (select auth.uid()) or c.sheet_visibility = 'campaign')
    )
  );

create policy "Owners add items"
  on public.character_items for insert to authenticated
  with check (
    exists (
      select 1 from public.characters as c
      where c.id = character_items.character_id
        and c.owner_id = (select auth.uid())
        and c.campaign_id in (select private.current_campaign_ids())
    )
  );

create policy "Owners update items"
  on public.character_items for update to authenticated
  using (
    exists (
      select 1 from public.characters as c
      where c.id = character_items.character_id
        and c.owner_id = (select auth.uid())
        and c.campaign_id in (select private.current_campaign_ids())
    )
  )
  with check (
    exists (
      select 1 from public.characters as c
      where c.id = character_items.character_id
        and c.owner_id = (select auth.uid())
        and c.campaign_id in (select private.current_campaign_ids())
    )
  );

create policy "Owners delete items"
  on public.character_items for delete to authenticated
  using (
    exists (
      select 1 from public.characters as c
      where c.id = character_items.character_id
        and c.owner_id = (select auth.uid())
        and c.campaign_id in (select private.current_campaign_ids())
    )
  );
```

Turning sharing off hides the items again on the next read, because there is no server-side copy.

### 3.3 Authorization matrix

Key: **R** read, **C** create, **U** update, **D** delete, **—** denied (no rows, or `42501`/`P0001`). "Member" means a current member who owns neither the campaign nor the character. "Departed owner" means the character's owner after leaving or removal.

| Action | Anon | Non-member | Member | Campaign owner | Character owner | Departed owner |
| --- | --- | --- | --- | --- | --- | --- |
| Read coins and items, sheet `private` | — | — | **—** | **—** | R | — |
| Read coins and items, sheet `campaign` | — | — | R | R | R | — |
| Add, spend coins (`adjust_character_currency`) | — | `character_unavailable` | `character_unavailable` | `character_unavailable` | yes | `character_unavailable` |
| Set a balance directly (`update … set gp`) | — | — | `42501` | `42501` | `42501` (no column grant) | — |
| Add an item | — | — | — (RLS) | — (RLS) | C (up to 200) | — |
| Edit or delete an item | — | — | — (0 rows) | — (0 rows) | U D | — |
| Change quantity by delta (`adjust_character_item_quantity`) | — | `item_unavailable` | `item_unavailable` | `item_unavailable` | yes | `item_unavailable` |
| Move an item to another character | — | — | — | — | `42501` (no column grant), and the guard for every path | — |

**Explicit negatives to test:** the campaign owner cannot read, add, change, or delete a member's private items or coins. A member who can read a shared sheet still cannot write its items or coins. No one can create an item for another player's character, move an item between characters, set a balance directly, drive a balance below zero, or exceed the item cap. A departed player loses every read and write, and remaining members stop seeing a departed player's items even if the sheet was shared.

## 4. Workflows and RPCs

### 4.1 Common prelude (same as M2 §4.1)

1. Reject null required arguments with `22023`.
2. Find the target (`characters` row, or the item's character) owned by the caller without a lock. If there is none, return the RPC's "unavailable" error.
3. Lock the campaign row `for share`, but only where the caller is a current member. If that fails, return the same "unavailable" error.
4. Lock the target row (`character_sheets` or `character_items`) `for update` and re-read it. If it is gone, return the same "unavailable" error.

### 4.2 `public.adjust_character_currency(...)`

```sql
create function public.adjust_character_currency(
  p_character_id uuid,
  p_cp integer default 0,
  p_sp integer default 0,
  p_ep integer default 0,
  p_gp integer default 0,
  p_pp integer default 0
) returns table (cp integer, sp integer, ep integer, gp integer, pp integer, updated_at timestamptz)
language plpgsql security definer set search_path = ''
```

| Step | Rule | Failure |
| --- | --- | --- |
| 1 | `p_character_id` not null. A null delta counts as 0. | `22023` / `currency_required` |
| 2 | Each delta between −9,999,999 and 9,999,999 | `22023` / `currency_amount_invalid` |
| 3 | Prelude (§4.1), with the caller as the character owner | `P0001` / `character_unavailable` |
| 4 | Every delta 0 → return the current balances (no-op, no write) | — |
| 5 | Any resulting balance below 0 → refuse the whole change | `P0001` / `currency_insufficient` |
| 6 | Any resulting balance above 9,999,999 → refuse the whole change | `P0001` / `currency_limit_exceeded` |
| 7 | `update … set cp = cp + p_cp, …` and return the new balances and `updated_at` | — |

- The deltas apply to the locked row, so concurrent adjustments from two devices both apply in order (D4). There is no lost update and no read-modify-write in the client.
- Steps 5 and 6 are checked in the RPC so the client gets a stable code. `character_sheets_currency_check` is the backstop.
- One call can change several denominations (for example, +5 gp and −3 sp after a trade). Either all of them apply or none do.
- The RPC returns `updated_at`, so the client can write it into the sheet cache. Without that, the next body save in the same tab would see a false conflict (§5.3).

### 4.3 `public.adjust_character_item_quantity(p_item_id uuid, p_delta integer) returns integer`

| Step | Rule | Failure |
| --- | --- | --- |
| 1 | Both arguments not null | `22023` / `item_required` |
| 2 | `p_delta` between −9,999 and 9,999 | `22023` / `item_quantity_invalid` |
| 3 | Prelude (§4.1), with the item's character owned by the caller | `P0001` / `item_unavailable` |
| 4 | Result below 0 | `P0001` / `item_quantity_insufficient` |
| 5 | Result above 9,999 | `P0001` / `item_quantity_invalid` |
| 6 | Update the quantity and return the new value. A zero delta returns the current value without writing. | — |

The item stays at quantity 0 rather than being deleted (D6). Deleting is a separate, explicit action.

### 4.4 Direct item writes

| Action | Request | Zero rows |
| --- | --- | --- |
| Add | `insert({ character_id, name, quantity, weight, description, equipped, attuned }).select(itemFields).single()` | RLS denial (`42501`) → "This character could not be updated by this account." `item_limit_reached` → its own copy. |
| Edit | `update({...}).eq('id', id).eq('updated_at', previous).select(itemFields).maybeSingle()` | `item_conflict` (client-side), refetch the items |
| Equip, unequip, attune | `update({ equipped })` or `update({ attuned })` with `.eq('id', id).select().maybeSingle()`. Last write wins: these are single toggles. | `item_unavailable` (client-side) |
| Delete | `delete().eq('id', id).select('id').maybeSingle()` | `item_unavailable` (client-side) |

The full edit form uses optimistic concurrency so a stale form cannot overwrite a newer description or quantity. Toggles and quantity deltas cannot conflict in a harmful way, so they skip it.

### 4.5 Concurrency

| Race | Outcome |
| --- | --- |
| Ten parallel `+1 gp` adjustments | All apply. The balance rises by exactly 10. |
| Balance 5 gp, ten parallel `−1 gp` spends | Exactly five succeed, five fail with `currency_insufficient`, and the final balance is 0. |
| Currency adjustment while the owner is removed | Removal first: the RPC fails with `character_unavailable`. RPC first: removal waits for it to commit. |
| Currency adjustment and a vitals or body save on the same sheet | Row lock serialization. Both apply. The adjustment bumps `updated_at`, so a body save sent afterwards with the older `updated_at` gets `sheet_conflict` (§5.3). |
| Five parallel item inserts at 199 items | Exactly one succeeds. Four fail with `item_limit_reached`. |
| Parallel quantity deltas on one item | All apply in order, and the result never goes below 0. |
| Item edit form saved on two devices | The second save matches no row (`item_conflict`). The client refetches and shows the latest. |
| Item insert while the owner leaves | Leave first: RLS denies the insert. Insert first: the item is kept like any other retained data. |
| Character deleted while an item is added | The delete's lock on the character row makes the insert's FK check wait. Afterwards the FK fails (`23503`), and the client shows the generic copy and refetches. |

Invariants after any interleaving (asserted by tests): no negative balance, no balance above the limit, no character with more than 200 items, no item quantity outside 0–9,999.

### 4.6 Error copy (frontend)

| Message | Copy |
| --- | --- |
| `currency_insufficient` | "You don't have enough coins for that. Nothing was spent." |
| `currency_limit_exceeded` | "A purse can hold up to 9,999,999 of each coin." |
| `currency_amount_invalid` | "Enter whole numbers of coins up to 9,999,999." |
| `item_limit_reached` | "A character can carry up to 200 different items. Remove one to add another." |
| `item_quantity_insufficient` | "There aren't that many left." |
| `item_quantity_invalid` | "Quantity must be between 0 and 9,999." |

## 5. Data shapes, validation, and derived values

### 5.1 Types

```ts
export const denominations = ['cp', 'sp', 'ep', 'gp', 'pp'] as const
export type Denomination = (typeof denominations)[number]
export type CharacterPurse = Record<Denomination, number>

/** A sheet row: vitals, body, and now the purse. */
export type CharacterSheet = CharacterVitals & CharacterPurse & {
  character_id: string
  updated_at: string
  sheet: CharacterSheetBody
}

export type CharacterItem = Tables['character_items']['Row']   // weight as number | null
export type CharacterItemInput = {
  name: string
  quantity: number
  weight: string        // as typed; '' → null
  description: string   // '' → null
  equipped: boolean
  attuned: boolean
}
```

PostgREST returns `numeric` as a number for values of this size. `toItem` coerces it with `Number()` in case it arrives as a string.

### 5.2 Validation layers

| Layer | Rules |
| --- | --- |
| Database | §2.1 currency check, §2.2 item checks, the 200-item cap, the RPC argument ranges. |
| Frontend (`inventoryValidation.ts`) | The same bounds with field-level messages: name required and trimmed, quantity a whole number 0–9,999, weight a number with at most two decimals 0–99,999.99 or empty, description up to 2,000 characters, coin amounts whole numbers 1–9,999,999 for add and spend (at least one non-zero). |

### 5.3 The sheet's `updated_at` and coin changes (D2 trade-off)

Currency lives on the sheet row, so every adjustment bumps `character_sheets.updated_at`, which is the body's optimistic-concurrency token.

- **Same tab**: `useCharacterActions` writes the RPC's returned balances and `updated_at` into the sheet cache (as it already does for vitals). An open body draft keeps its edits (`SheetContent` is keyed by character id) and saves against the new token. No false conflict.
- **Another device**: a coin change on device B makes device A's pending body save fail with the existing `sheet_conflict` copy. This already happens today when vitals change on another device. It is accepted for M3 and listed as a risk. If it proves annoying, the fix is a body-only revision column (a later migration), or D2's alternative.

### 5.4 Derived values (client only, never stored)

| Value | Rule |
| --- | --- |
| Total coin value | `cp/100 + sp/10 + ep/2 + gp + pp*10`, shown as "≈ 123.45 gp". |
| Carried weight | Σ `weight × quantity` over items with a weight (D9). |
| Carrying capacity | Strength score × 15 lb, from the sheet body. |
| Attuned count | Shown with a warning above 3 (D7). |

They go in `inventoryRules.ts`, next to `characterSheetRules.ts`.

- `useCharacterActions` keeps one pending state, now `{ action, characterId, itemId }`, so the dialog's close-blocking (`isDeleting`) covers M3 writes with no workspace change.
- `currency`: the RPC result is merged into the sheet cache (balances and `updated_at`). No refetch.
- `item-add`, `item-edit`, `item-equip`, `item-quantity`, `item-delete`: update the items cache from the returned row (append, replace, or remove), then invalidate the items key in the background. On `item_conflict` or `item_unavailable`, refetch the items.
- `character_unavailable`: refetch characters, as M2 does. Deleting a character also removes its items key.
- `useCampaignMembership` already marks the `['campaigns','characters']` prefix keys stale on leave and invalidates them on remove. The items key sits under that prefix. Phase 3 verifies this with a test and adds the key explicitly if the existing calls use exact keys.

### 6.4 Accessibility and layout

- Every async surface has loading (`role="status"`), error with retry, empty, and success states. Focus moves into a form when it opens and back to its trigger on cancel or save. It moves to the confirm button when a removal confirmation opens.
- Quantity buttons have at least 44 px targets. The coin form stacks to one column at phone width. Checked with Playwright captures at 390, 820, and 1440 px, with no horizontal scroll.
- Numbers use `inputMode="numeric"` (coins, quantity) and `inputMode="decimal"` (weight).

## 8. Non-destructive migration strategy

### 8.1 Files (timestamps after `20261114151000`; use the real creation time)

| # | File | Contents |
| --- | --- | --- |
| 1 | `20261114160000_add_character_inventory.sql` | Currency columns and check on `character_sheets`. `character_items` with constraints, index, guard and `updated_at` triggers, RLS, revokes, grants, and policies. |
| 2 | `20261114161000_add_inventory_rpcs.sql` | `adjust_character_currency` and `adjust_character_item_quantity` (revoke all, EXECUTE to `authenticated`). |

Each is wrapped in `begin; … commit;`. The only change to an existing object is the five added columns and one check on `character_sheets`: additive, with constant defaults, and no grant changes. No existing policy, grant, function, or trigger changes. No backfill is needed, because the defaults give every existing sheet an empty purse.

### 8.2 Pre-flight (read-only)

1. `git status` is clean, or contains M3 changes only.
2. `npm run supabase:status`. `schema_migrations` lists exactly the sixteen versions in §1.5.
3. Baseline in a read-only transaction: row counts of `profiles`, `campaigns`, `campaign_members`, `campaign_invitations`, `characters`, `character_sheets`, `campaign_appearances`. The M1 ownership-consistency query (0 rows). Table, column, and function ACLs on `character_sheets` and the character RPCs.
4. Optional local safety net outside the repo: `docker exec supabase_db_backend pg_dump -U postgres --data-only --schema=public --schema=auth -Fc > <scratchpad>/pre-m3.dump`.
5. Baseline suites: `npm run lint`, `npm run format:check`, `npm run build`, `npm test`, `npm run test:e2e`, `npm run test:local-supabase`.

### 8.3 Apply

One migration per phase with `npm run db:migrate` (from `implementation/backend`). A failure rolls the file back and the CLI does not record it. Then run `npm run db:types` and `npx prettier --write src/types/database.ts`. Never run `db:reset`.

### 8.4 Post-migration checks (read-only)

| Check | Expected |
| --- | --- |
| Existing row counts | Identical to baseline (profiles may rise only from test accounts) |
| The existing sheet | Same vitals and body. `cp…pp = 0`. |
| `relrowsecurity` on `character_items` | true |
| `has_column_privilege` on `character_sheets` | `authenticated`: select on `cp…pp`, **no** update on `cp…pp`. Existing column grants unchanged. |
| `has_table_privilege` / `has_column_privilege` on `character_items` | `authenticated`: select, delete, the listed insert and update columns, no update on `character_id`. `anon`, `service_role`, `public`: none. |
| `has_function_privilege` | Both RPCs: `authenticated` only. `private.guard_character_item_write`: nobody but `postgres`. |
| Existing function and table ACLs | Unchanged |

### 8.5 Rollback (compensating migrations only)

| Migration | Compensation | Data impact |
| --- | --- | --- |
| 2 | Drop both RPCs. | Balances freeze (read-only). Items stay editable directly, except quantity deltas. |
| 1 | Drop `character_items`, the guard function, the currency check, and the five columns. | **Deletes all items and balances.** Only acceptable before real use. Otherwise export first. |

### 8.6 Test-data safety

Integration tests create their own accounts, campaigns, and characters, and delete their campaigns in `finally` (items and coins cascade). Counts are scoped to the test's own campaigns (lesson from M03.2 Phase 5, note 1). Destructive SQL (direct writes as `postgres`, invariant violations) runs inside `begin; … rollback;` through `localDatabaseQuery`. The existing character, sheet, and other pre-existing rows are never touched.

### 9.1 Integration — `e2e/local-supabase-inventory.spec.ts` (new)

Uses `e2e/support/localPlayers.ts`. Characters are created through `create_character`, and members join through the real invitation RPCs. Added to `test:local-supabase`.

**Catalog and privileges** (read-only): exactly as §8.4.

**Currency**
- A new character's sheet has all five balances at 0.
- Add and spend across several denominations in one call. The returned balances and `updated_at` match the row.
- Spending below zero → `currency_insufficient`, and no denomination changes (including the ones that would have stayed positive).

- A direct `update character_sheets set gp = …` by the owner → `42501`.

**Items**
- The owner adds, edits, equips, attunes, changes quantity, and deletes. Each returns the row, and `updated_at` advances.
- Normalization and checks: blank name, a name over 80 characters, a description over 2,000 characters, a control character, quantity −1 or 10,000, and weight 100,000 → `23514`. A description with newlines is accepted.
- Item 201 → `item_limit_reached`.

- `adjust_character_item_quantity`: below zero → `item_quantity_insufficient`. Out of range → `item_quantity_invalid`. Non-owners, departed owner, or unknown item → `item_unavailable`.

**Bypass attempts through the API** (publishable key, signed-in member)
- Inserting an item for another player's character, or for a character in a campaign the caller is not in → `42501`.
- Updating `character_id` → `42501`. Updating or deleting another player's item → 0 rows, row unchanged (checked with `localDatabaseQuery`).
- Inserting with an explicit `id` or `created_at` → `42501`.

**Bypass attempts in the database** (as `postgres`, rolled back)
- Changing `character_id` → `item_reassignment_forbidden`.
- A 201st item → `item_limit_reached`.
- A negative balance → `23514`.

**Visibility**
- Private sheet: another member and **the campaign owner** read no items, and no balances (no sheet row). The owner reads both.
- Shared sheet: every current member reads items and balances but cannot write either. After unsharing, they are hidden again.

**Departure and rejoin**
- The owner leaves: items and balances are unchanged (`localDatabaseQuery`). The leaver reads and writes nothing (`character_unavailable`, `item_unavailable`, RLS denial on insert). Remaining members no longer see the shared items. Removal behaves the same.
- Rejoin: the same items and balances are readable and writable again.

**Cascades** (counts scoped to the test's campaigns)
- Deleting the character removes its items. Deleting the campaign removes every item in it, including a departed player's.

**Concurrency** (`Promise.all` from separate clients)
- Ten parallel `+1 gp` → +10.
- 5 gp and ten parallel `−1 gp` → five successes, five `currency_insufficient`, final 0.
- Five parallel inserts at 199 items → one success.
- Parallel quantity deltas → all applied, never below 0.
- Currency adjustment racing `remove_campaign_member` → either applied or `character_unavailable`, and never an error of any other kind.
- After each: the §4.5 invariants hold (SQL assertions).

**Sheet token**: after an adjustment, a body save with the returned `updated_at` succeeds. With the earlier token it matches no row (documents §5.3).

**Regression**: the four existing specs pass unchanged.

**UI against the real stack** (same file, kept light: one context at a time, reduced motion, one worker): a player adds coins and an item in the tent and reloads, and both persist. A second player opens the shared sheet from the Party panel and sees both, read-only.

## 11. Acceptance criteria (M3 as a whole)

1. A character's owner can add, edit, equip, attune, change the quantity of, and remove items, and add and spend coins, from the tent's display and edit views. Every change persists across a reload.
2. Balances never go negative or above the limit, and concurrent adjustments from several devices all apply. The same holds for item quantities.
3. No character has more than 200 items, including under concurrent inserts and direct database writes.
4. Items can never move to another character, and balances can be changed only through the RPC.
5. Items and coins are visible to exactly those who can read the sheet. The campaign owner has no override, and other members never write them.
6. Leaving or removal keeps items and coins and revokes all access, including other members' view of a shared sheet. Rejoining restores it.
7. Deleting a character or a campaign removes its items and coins after a confirmation that says so.
8. Existing auth, campaigns, invitations, membership lifecycle, display names, characters, sheets, portraits, appearances, and camp behaviour are unchanged, and their tests pass.
9. Migrations ran with `db:migrate` only, existing row counts and the existing sheet are unchanged, and no `db:reset` was run. All §9.4 commands pass and are reported.

## 12. Risks and edge cases

### Risks

| Risk | Mitigation |
| --- | --- |
| Coin changes on one device make a pending body save on another device conflict (§5.3) | Same-tab adjustments update the token in the cache. The cross-device case shows the existing conflict copy. A body-only revision column, or D2's alternative, is the follow-up if this happens often. |
| Nested RLS (items → characters → roster) slows reads as inventories grow | Index on `character_id`, a cap of 200 items, and one query per opened sheet. Revisit with `explain` if needed. |
| The item cap trigger's `for no key update` briefly blocks character RPCs on the same character | Single-row inserts that commit in milliseconds. Lock order stays `characters` → items. |
| The client's bounds drift from the database checks | One source of limits in `inventoryValidation.ts`, mirrored by the SQL. The integration tests send every boundary. |
| Quick `+`/`−` taps fire many RPCs | Each is a tiny atomic update. Buttons stay enabled for rapid taps, and pending state is per item, so other items stay usable. Tests assert ordered results. |
| A shared sheet now exposes wealth and gear to every member (D1) | Copy beside the sharing toggle: "Members can see this sheet, including coins and inventory." |

### Edge cases covered

- Spending with insufficient coins changes nothing, including other denominations in the same call.
- A double-submitted add form → two items. Accepted, because items are not unique. The second is easy to remove, and the submit button is disabled while pending.
- Quantity 0 keeps the item ("used up"). Removal is explicit.
- An item open in the edit form is deleted on another device → `item_unavailable` and the list refreshes.
- The sheet is unshared while a member views it → the next read returns nothing, and the panel shows "This sheet is no longer available." (existing behaviour).
- A retired or deceased character keeps an editable inventory (M2 R2).

### Open questions for later milestones (no M3 action)

- **M7 Realtime**: push balance and HP changes to other open views of a shared sheet.
- **M8 Imports**: the legacy import shape (`inventory: [{ name, quantity, description }]`, `currency: { gp, sp, cp }`) maps directly to `character_items` and `adjust_character_currency`. An import must go through the same paths, so the cap, bounds, and visibility still hold. Decide then whether an import sets balances (it would need a set-with-expected-balance RPC) or proposes deltas.
- **Party features**: giving items or coins between characters, and a shared party stash, if the group wants them (D10).
