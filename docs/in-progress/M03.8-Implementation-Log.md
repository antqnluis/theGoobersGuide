### Deviations from the plan

1. **Lock order for `apply_character_update`.** The plan locks the character row, then the sheet. A SECURITY INVOKER function cannot lock the campaign row (members have no UPDATE policy on it), and the inner coin function then takes the campaign lock while the character is already locked, which can deadlock with a concurrent leave. The function instead starts with `adjust_character_currency(p_character_id, 0, 0, 0)`: it locks the campaign `FOR SHARE` and the sheet `FOR UPDATE` in the existing order, returns `character_unavailable` for unknown, inaccessible, other people's, and departed characters, and changes and logs nothing. The character row is locked next. No new SECURITY DEFINER function was needed. The departure-race test covers it.
2. **Optional `change_count` in `p_changes`.** The review's count of selected changes cannot be derived from a full replacement sheet body, so `p_changes` accepts an optional integer `change_count` (1–100,000). Without it, the function derives a count (detail keys, vital keys, one for the sheet, each item add, update, and remove, and coin keys). It is informational only. Phase 4 should send it.
3. **Stricter payload shape.** Both RPCs check every key and type before writing: unknown keys, wrong types, and application-owned keys give `import_invalid`; coins outside 0–9,999,999 also give `import_invalid`; values the database's own checks refuse give `import_values_invalid`. All five top-level keys are required for a new import (`vitals`, `items`, and `coins` may be empty). `p_expected.items` must list every item the update targets.
4. **Helper fix applied in place.** The first run of the spec found `field_keys || 'id'` in `private.import_item_is_valid` being read as an array literal. The function was re-created with `'id'::text` directly in the local database and the migration file was corrected to match. Nothing else had used the migration yet, and no reset was done; a fresh `db:reset` would produce the same state.
5. **Extra private helpers.** The shape checks are small private functions (listed above), each `EXECUTE` for `authenticated` so the invoker RPCs can call them.

No UI, prompts, or document parsers (Phases 2–5). `docs/reference/DATABASE_SCHEMA.md` is not updated yet (Phase 5).

### Decisions within the plan

1. **Invalid documents still show their content.** `parseCharacterDocument` always builds a best-effort character (an invalid field takes its default) next to the list of issues, so the Phase 3 review can show every section with its errors. Only a document that fails the envelope check is rejected outright.
2. **Unsupported coins are errors, not ignored keys.** An `ep` or `pp` amount would silently lose money, so the document is reported (with a "convert other coins first" message) in both formats; the prompts also tell the assistant to convert them.
3. **Skill and ability keys that are unknown are errors**, as in plan §2.1. Other unknown keys are listed as not imported.
4. **Update validity per change.** A change's own value is checked alone (type and range). Relations between changes, such as current HP against maximum HP, the item cap, the attack cap, and the saved size of the sheet, are checked in `toUpdatePayload` against the selection, so selecting only the current-HP change when it exceeds the stored maximum fails with a clear message instead of reaching the database.
5. **`toUpdatePayload` sends `change_count`** (the number of selected changes), using the optional key added in Phase 1.
6. **Code fences.** One surrounding Markdown code fence is stripped before JSON parsing, because outside assistants commonly add one. Nothing else in the text is interpreted.

### Change request after Phase 3 — precise conversion and update prompts (2026-11-15)
