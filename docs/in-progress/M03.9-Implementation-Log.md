## Phase 1 — Schema, RPCs, and types (2026-11-22) — done

One migration, `20261122210000_add_adventure_handoffs.sql`, applied with `npm run db:migrate` (not `db:reset`). It follows plan §3, with the deviations listed below. No UI changes.

**What was added**

- `public.adventure_handoffs` with RLS on. `authenticated` has `select` and `delete` only. Policies: "Readers see sources" (`visible_adventure_ids`) and "Importers delete their sources" (importer, `editable_adventure_ids`). A before-insert trigger enforces the 50-source cap under an advisory lock. The table is in `supabase_realtime` with default replica identity.
- `adventure_objectives.handoff_id` and `adventure_updates.handoff_id` (nullable, `on delete set null`, partial indexes). No new column grants, so clients cannot set them.
- `public.attach_adventure_handoff` and `public.create_adventure_from_handoff`, both SECURITY INVOKER with `search_path = ''`.
- Private helpers: `lock_handoff_target` and `record_adventure_handoff` (SECURITY DEFINER), `handoff_changes_are_valid` and `normalize_handoff_label` (invoker). They reuse M03.8's `import_has_only_keys`, `import_is_uuid`, and the existing `lock_adventure_campaign` / `lock_adventure_row`.
- `src/types/database.ts` regenerated with `npm run db:types` and formatted with Prettier (the generator's own formatter hint produces a different style). The test factories in `adventureTestData.ts` gained `handoff_id: null`.
- `e2e/local-supabase-handoffs.spec.ts` (21 tests), added to `test:local-supabase`.

**Deviations from the plan**

1. **Source-only attach ignores `p_expected`.** When `p_changes` is `{}`, nothing is read or compared, so a source-only attach does not fail because someone else edited the adventure meanwhile. When anything changes, `p_expected` is required and strict, as planned.
2. **Shape is checked before the lock** (plan step 2 came after it). Garbage input fails with `handoff_invalid` without taking locks. The shape check reads no tables, so nothing leaks.
3. **Archived targets raise `adventure_archived`** from `lock_handoff_target` (plan edge case). Unknown, unreadable, and departed targets raise `adventure_unavailable`.
4. **Source text** has CRLF and lone CR normalised to LF by `record_adventure_handoff` before the check, so the stored text has no `\r` and the table check disallows it, matching "no control characters except newline and tab". A source with no non-whitespace character is also refused (`handoff_source_invalid`). Both are small additions to H11.
5. **`create_adventure` errors pass through** (for example `adventure_title_invalid` for a title over 120 characters), as the plan's "known codes pass through" says. `handoff_values_invalid` covers rules that only the handoff's own writes can break (status, reference, objective and update bounds).
6. **`applied`** always holds all four keys: `fields` (sorted), `objectives_added`, `objectives_changed`, `update`.

**Coverage of plan §8.1**

- Attach as a sole participant, with rename, complete, reopen, add, and update, and tagging of new rows only. Source-only attach. Main-adventure attach by any member, readable by all.
- Negatives: campaign owner, pending invitee, and party reader on a private or shared thread. A party reader reads sources while the thread is shared and loses them when consent is withdrawn. A departed member can neither attach nor read. A non-member and an unknown id look the same.
- Forbidden keys (`visibility`, `type`, `archived_at`, participants, consent) fail with `handoff_invalid`. Clients cannot write `handoff_id` or insert or update sources. `record_adventure_handoff` does not tag rows that existed before the transaction, whoever created them. Neither helper is reachable through the API.
- Conflicts: an edit to the adventure or to a targeted objective fails the whole apply. An objective from another adventure, or a deleted one, also fails. Two concurrent handoffs on the same versions apply once and conflict once. A handoff racing `leave_campaign` lands before it or is refused after it.
- Caps: the 51st source and objectives past 50 roll back the whole import.
- Deletes: only the importer, refused while archived, linked rows keep their content with `handoff_id` null, account deletion cascades sources, and deleting the campaign removes them.

**Not covered yet:** the `update` cap (500) is not exercised by a handoff, because it is the existing trigger and Phase 1 does not change it.

### Notes for Phase 2

- The frontend must pass `updated_at` strings back to the RPC exactly as PostgREST returned them. Round-tripping through `Date` would truncate microseconds and cause false conflicts.
- A handoff proposal's `title` may not be cleared, and an objective op may name an id only once. The RPC enforces both, so `handoffChanges.ts` should mirror them.

## Phase 2 — Format, prompt, and parser (2026-11-22) — done

Pure TypeScript with unit tests. No UI, migration, or database changes, so `test:local-supabase` was not rerun (nothing it covers changed).

**What was added** (all under `implementation/frontend/src/features/`)

- `characters/importText.ts`: `checkEnvelope` now takes an optional table of wrong-format messages (expected format → found format → message), which defaults to `wrongFormatMessages`. Added `documentFormats.handoff`, `handoffDocumentVersion`, and `regenerateHandoffMessage`. Character and update behaviour and messages are unchanged. New `importText.test.ts` covers the envelope for all three formats.
- `adventures/handoffDocument.ts`: `parseHandoff(text, target)` returns `rejected` (blocking) or `parsed` with a list of `HandoffChange`, the assistant's `notes`, and `ignored` keys. Each change has a stable key, current and proposed values, a state (`ok`, `unchanged`, or `invalid` with a message), and `suggestsCompletion`. It also exports `HandoffTarget`, `blankTarget`, and `handoffTargetFrom`.
- `adventures/handoffPrompt.ts`: `handoffPrompt({ sourceText, current?, hint? })`. With `current` it builds the attach prompt (current values with objective ids, description merge rule). Without it, the new-adventure prompt (add-only objectives, optional focus hint). The handoff text sits between fixed start and end marker lines. All limits come from `adventureLimits`.
- `adventures/handoffChanges.ts`: `defaultSelection` (H6, H7), `selectedChanges`, `buildAttachRequest` (database-shaped `p_changes`, `p_expected`, and a count; empty selection becomes a source-only attach), `buildNewRequest` (title required, status from the player), and `completionSuggestions`.
- `adventures/adventureValidation.ts`: `validateAdventureField`, so the parser reuses the form's own limits and does not copy them.
- `adventures/handoffTestData.ts`: shared test fixtures.

**Decisions made while implementing**

1. **What blocks a document** (H8): invalid JSON, wrong format or version, a missing `proposal`, an objective id that is not on the adventure (this includes a new adventure, which has no objectives), the same objective used twice, an unknown or malformed objective operation, and more than 50 operations. Everything else disables only its own change: a bad or wrong-typed value, an empty or over-long title, a status outside the four values, a missing objective title, and an update that is empty-of-text or too long.
2. **Unknown keys** are listed, never blocking: top-level keys, `proposal.*`, and keys inside an operation. `visibility`, `type`, and `participants` fall under this, so they never reach the payload.
3. **`null` is not "clear".** A field is cleared with `""`. `null` for a text field disables that change, with a message that says so.
4. **Objective cap in the review.** Adds that would pass 50 objectives are shown as invalid ("An adventure can have 50 objectives."), so the database cap does not surprise the player.
5. **New adventure status.** In new mode a proposed status is never preselected (H6). `buildNewRequest` uses an explicit status if given, then a selected status change, else the adventure stays Pending.
6. **Empty `update`** (blank text) proposes nothing and is dropped.
7. **Notes** from `issues` are trimmed, empty ones dropped, at most 20, each cut at 500 characters. A malformed `issues` is listed as ignored.

**Tests** (57 new): the envelope for all formats; every blocking case and every per-value case; ignored keys; H7 suggestions; the cap; payload building from selections, including exact `updated_at` strings; the prompt's embedded current values, markers, and data-only rules; each stated limit checked against the parser at the limit and one over; and the prompt's own examples parsed by the parser.

### Notes for Phase 3

- The dialog must read `updated_at` from the adventure and every objective and pass those strings straight into `buildAttachRequest`. Do not parse them into `Date` values.
- A conflict reload should rebuild `HandoffTarget` from the fresh adventure, re-run `parseHandoff` on the same text, and start with an empty selection. A now-unknown objective id comes back as `rejected`, which the dialog shows with the "copy the prompt again" message.
- The review should show `suggestsCompletion` changes with "The handoff suggests this. Only you decide it's done." and list `notes` at the top and `ignored` under "Not imported".
