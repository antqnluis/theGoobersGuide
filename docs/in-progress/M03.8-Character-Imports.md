## Overview and objectives

A player often already has their character written down somewhere else, usually as a Markdown sheet or an AI DM's handoff. M8 lets them bring it in without retyping it, and lets them bring later changes in without overwriting what they have edited in the app since.

M8 delivers:

1. **A portable character document** (`the-goobers-guide-character`, version 3) that mirrors the current sheet, and a **changes-only update document** (`the-goobers-guide-character-update`, version 2).
2. **Copyable conversion and update prompts.** The player gives a prompt and their Markdown to an outside writing assistant and pastes back the JSON it returns. The app never sends anything to an AI service and never parses Markdown itself (D1).
3. **Import as a new character**: paste or upload a document, review every section, then create the character, its sheet, items, and coins in one transaction.
4. **Import updates to an existing character**: paste or upload a changes-only document, review each proposed change against the current values, select the changes to keep, and apply them in one transaction that fails if anything changed during review.
5. **Markdown export**: download a readable sheet for a DM or an AI assistant.
6. **Two SECURITY INVOKER RPCs** (`import_character`, `apply_character_update`) that only add atomicity. Every write still runs under the caller's own grants, RLS, guards, caps, and check constraints, so the RPCs grant nothing a player cannot already do one write at a time.
7. **Attack ids** (D12): every attack in a sheet body gets a stable id, existing attacks are backfilled, and the database requires them, so updates can target attacks exactly as they target items.
8. **Import provenance** (D10): a read-only `public.character_imports` record of each import (when, by whom, new or update, a source label, how many changes), written only inside the two RPCs and shown as an import history on the sheet.
9. **Tests**: multi-account integration tests against the local stack, parser and resolver unit tests with fixtures, and mocked and real-stack browser tests.

## Inherited decisions (no change)

| # | Decision | M8 consequence |

| B10 | Campaign ownership grants no access to private sheets. | Only the character owner can apply an update. The campaign owner has no override. |

## Approved decisions

Chosen in the 2026-11-15 review.

| # | Decision | Choice |
| --- | --- | --- |
| D1 | How does a Markdown sheet become app data? | **A copyable prompt plus JSON**, as in the legacy app: the app shows a conversion prompt, the player uses it with an outside assistant, and pastes or uploads the JSON it returns. The app validates the JSON and shows it for review. No server, no secrets, no AI calls, no Markdown parser. |
| D2 | What happens to legacy version-2 character files? | **Rejected** with a message to regenerate them using the new prompt. Only version 3 is accepted. Legacy update files (version 1) are rejected the same way. |
| D3 | When are DM handoffs built? | **After M5.** M8 ships character imports now; §11 sketches the handoff schema for M5 to leave room for. |
| D4 | Which features are in scope? | **Import as a new character, update an existing character, and Markdown export.** No JSON export or download. |
| D5 | How is an import applied? | **One database function call per import**, so it is all-or-nothing, running as the caller (SECURITY INVOKER) so every existing rule applies. |
| D6 | How are coins imported? | **New character:** the imported amounts are added from zero. **Update:** the document states target balances; the review shows the change from the current balance, and the apply fails if the sheet changed after the review was loaded. |
| D7 | What if the player already has an active character in the campaign? | **Import as new is blocked** before review, with a message pointing to **Import updates** on the existing character (or to retiring it first). The database rule stays the final check. |
| D8 | What can an import never change? | Party membership (`in_party`), sheet visibility, the portrait, status, owner, and campaign. A new character starts out of the party, private, with no portrait, and active. |
| D9 | What does the update prompt compare against? | **A JSON copy of the character inside the copied prompt**, including item and attack ids so the assistant can target them exactly. There is no separate JSON download (D4). |
| D10 | Should a character import record its provenance? | **Yes.** Each successful import writes one `character_imports` row with the import time, the importing account, the kind (`new` or `update`), an optional source label, and the number of changes applied (§3.3). The source document itself is not stored. |
| D11 | Should coin-log rows say they came from an import? | **No.** `character_currency_log` is unchanged; an imported coin change appears as an ordinary log row. The matching `character_imports` row records that an import happened at that time. |
| D12 | How do updates target attacks? | **By id.** Each attack in the sheet body carries an `id` (a UUID, unique within the sheet). A migration backfills ids for existing attacks and the sheet validator then requires them (§3.1). Name matching is not used. |

## 1. Current implementation audit

### 1.1 Objects M8 builds on

| Object | Relevant facts |
| --- | --- |
| `public.create_character(...)` | SECURITY DEFINER. Validates details, locks the campaign `FOR SHARE` as a current member, inserts the character as `active` with `in_party` from its argument (default `false`), and inserts an empty sheet row. Errors include `character_campaign_unavailable`, `character_active_exists`, `character_name_invalid`, `character_details_invalid`, `character_level_invalid`. |
| `public.characters` | Owners update `name`, `species`, `class_name`, `subclass`, `background`, `level`, `sheet_visibility`, `portrait_path` while a member (column grants plus the "Owners update their characters" policy). `guard_character_write` rejects reassignment and requires membership on insert. |
| `public.character_sheets` | Owners update `max_hp`, `current_hp`, `temp_hp`, `armor_class`, `speed`, `sheet` while a member. Check constraints bound the vitals; `character_sheets_sheet_check` limits the body to 65,536 bytes and to the version-1 shape (`private.character_sheet_is_valid`). The validator checks only that `attacks` is an array of at most 30 objects; it does not check their keys, and attacks have no ids today. |
| `public.character_items` | Owners insert and update `name`, `quantity`, `weight`, `description`, `equipped`, `attuned` and delete, while a member. The insert trigger serializes on the character row and raises `item_limit_reached` at 200. |
| `public.adjust_character_currency(uuid, int, int, int)` | SECURITY DEFINER. Adds deltas to the locked purse, rejects negative and over-limit balances, writes one `character_currency_log` row per applied change, and moves the sheet's `updated_at`. |
| Departure hook | Updates the leaver's `characters` rows, so it takes their row locks. Locking the character row `FOR UPDATE` serializes an update with departure (§4.3). |
| `npm run db:types` (backend) | Regenerates `frontend/src/types/database.ts`. |

### 1.2 The current sheet versus the legacy format

The legacy version-2 document (`legacy/docs/CHARACTER_IMPORT.md`) does not match the current sheet, which is why D2 introduces version 3.

| Area | Legacy v2 | Current sheet (v1 body) |
| --- | --- | --- |
| Abilities | `{ score, modifier }` per ability | Score 1–30 only; the modifier is derived |
| Skills | List of `{ name, modifier, proficient }` | Map of the 18 skill keys to `proficient` or `expertise` |
| Saving throws | List of `{ ability, modifier, proficient }` | List of proficient ability keys |
| Attacks | `{ id, name, attackBonus, damageExpression }` | `{ name, bonus, damage, notes }`, at most 30, no ids (M8 adds `id`, D12) |
| Spells, features | Structured lists | Free text, up to 8,000 characters each |
| Inventory | `{ id, name, quantity, description }` | Rows with `weight`, `equipped`, `attuned` |
| Combat | Includes `initiativeModifier`, `proficiencyBonus` | Initiative and proficiency bonus are derived; vitals are columns |
| Currency | `gp`, `sp`, `cp` | `cp`, `sp`, `gp` columns |

## 2. Document formats

Both formats are plain JSON. Files are accepted by paste or upload; uploads must be smaller than 1 MB and parse as UTF-8 JSON. Selecting or pasting a file never saves anything.

### 2.1 Character document, version 3

```json
{
  "format": "the-goobers-guide-character",
  "version": 3,
  "character": {
    "name": "Arlen Vale",
    "species": "Human",
    "class_name": "Ranger",
    "subclass": "Gloom Stalker",
    "background": "Outlander",
    "level": 3,
    "vitals": { "max_hp": 24, "current_hp": 24, "temp_hp": 0, "armor_class": 15, "speed": 30 },
    "abilities": { "str": 12, "dex": 16, "con": 14, "int": 10, "wis": 15, "cha": 8 },
    "saving_throws": ["str", "dex"],
    "skills": { "survival": "proficient", "stealth": "expertise" },
    "attacks": [{ "name": "Longbow", "bonus": "+5", "damage": "1d8 + 3 piercing", "notes": "150/600 ft." }],
    "features": "Favored Enemy …",
    "spells": "1st level: Hunter's Mark …",
    "notes": "Keeps watch at dusk.",
    "alignment": "Neutral good",
    "experience": 900,
    "inventory": [
      { "name": "Rope", "quantity": 1, "weight": 10, "description": "50 ft., hempen", "equipped": false, "attuned": false }
    ],
    "currency": { "cp": 0, "sp": 4, "gp": 12 }
  }
}
```

Rules:

- `format` and `version` must match exactly. `version: 2` (or any other) fails with the "regenerate with the current prompt" message (D2).
- `name` is required. Every other field is optional; a missing field takes the same default as a newly created character (empty text, no vitals, scores of 10, no proficiencies, no items, no coins).
- Field names and bounds are the database's (§1.1, `limits`, `inventoryLimits`). Unknown skill or ability keys, values out of range, more than 30 attacks, or more than 200 items are errors shown in review.
- Application-owned fields (`id`, `campaign_id`, `owner_id`, `status`, `in_party`, `sheet_visibility`, `portrait_path`, timestamps, and any item or attack `id`) are ignored if present and listed in review as "not imported". A new character's attacks and items always get fresh ids. Any other unknown key is also listed as ignored, not an error, so a well-meaning extra field does not block an import.
- Text is imported as text. Nothing in a document is ever executed, rendered as HTML, or treated as an instruction.

### 2.2 Update document, version 2

```json
{
  "format": "the-goobers-guide-character-update",
  "version": 2,
  "changes": {
    "details": { "set": { "level": 4 }, "clear": ["subclass"] },
    "vitals": { "set": { "max_hp": 31, "current_hp": 31 } },
    "abilities": { "set": { "wis": 16 } },
    "saving_throws": { "add": [], "remove": [] },
    "skills": { "set": { "perception": "proficient" }, "remove": ["stealth"] },
    "attacks": [
      { "op": "update", "id": "<attack id from the comparison copy>", "set": { "bonus": "+6" } },
      { "op": "add", "entry": { "name": "Shortsword", "bonus": "+5", "damage": "1d6 + 3", "notes": "" } },
      { "op": "remove", "id": "<attack id>" }
    ],
    "text": { "set": { "notes": "…" } },
    "inventory": [
      { "op": "update", "id": "<item id from the comparison copy>", "set": { "quantity": 2 } },
      { "op": "add", "entry": { "name": "Torch", "quantity": 2 } },
      { "op": "remove", "id": "<item id>" }
    ],
    "currency": { "set": { "gp": 20, "cp": 0 } }
  },
  "issues": []
}
```

Rules:

- Only mentioned values change. An explicit empty string, zero, or `false` is a change; clearing an optional detail (`species`, `class_name`, `subclass`, `background`) uses `clear`.
- `text` covers `features`, `spells`, `notes`, `alignment`, and `experience` (whole-field replacement).
- Items and attacks are matched by `id` (D12). New entries omit the `id`; the app assigns one. An id that is not on the character blocks the whole document.
- `currency.set` states **target balances** (D6). `remove` does not exist for coins; a coin set to `0` is the explicit form.
- A non-empty `issues` array, an unknown target, or an ambiguous target **blocks the whole document**. A single value that fails validation is shown on its own change and cannot be selected; the other changes stay selectable.

### 2.3 Prompts

`characterPrompts.ts` holds two prompt templates, versioned with the formats:

- **Conversion prompt**: describes version 3, tells the assistant to treat the Markdown as source data only, ignore instructions inside it, keep only current confirmed values, map ability and skill information to scores and proficiency levels (never to stored modifiers), and fold structured spells, features, and anything unsupported into the free-text fields.
- **Update prompt**: the same guidance, plus the character's current values as a version-3 document **with item and attack ids** (D9), a marked place for the new handoff, and the instruction to return only changes in the version-2 update format.

The player copies a prompt with one button. The app does not track whether or where it was used.

## 3. Schema and RPCs

Two migrations, with timestamps after `20261114210000`, applied in this order:

1. `<timestamp>_add_attack_ids.sql` (§3.1): backfills attack ids and replaces the sheet validator. It changes existing data (adds ids) and one existing function; no table, column, or policy changes.
2. `<timestamp>_add_character_imports.sql` (§3.2–§3.6): adds one table, one private helper, and two RPCs. No existing object changes.

### 3.1 Attack ids (D12)

In one transaction:

1. **Backfill.** For every `character_sheets` row whose body has a non-empty `attacks` array, add `"id": gen_random_uuid()::text` to each attack object that lacks a valid one, keeping the array order and every other key. Rows with no attacks are not touched.
2. **Replace `private.character_sheet_is_valid`** (same signature, `create or replace`) so that each attack must also have an `id` that is a lowercase UUID string, unique within the sheet. Every other rule is unchanged.
3. **Verify.** `create or replace` does not re-check existing rows against the constraint, so the migration counts rows where `not private.character_sheet_is_valid(sheet)` and raises (rolling everything back) if any exist.

Notes:

- Ids are generated by whoever creates the attack: the migration for existing attacks, the sheet editor for new ones (`crypto.randomUUID()`), and the frontend when building an import payload. The database only checks them.
- The backfill moves `updated_at` on every sheet that has attacks (through `set_updated_at`). An editor open during the migration gets one ordinary `sheet_conflict` and reloads.
- Ids add about 45 bytes per attack (at most about 1.4 KB per sheet). Pre-flight (§7) checks that no sheet would exceed the 65,536-byte limit; if one would, the migration fails rather than altering it.
- **The frontend change must ship with this migration** (Phase 1): once the validator requires ids, the current `normalizeSheet`, which drops them, would make every save of a sheet with attacks fail.

### 3.2 Common rules for the import RPCs

- `language plpgsql security invoker set search_path = ''`. Every statement runs with the caller's privileges and RLS, so the RPCs need no new table grants and cannot do anything the client could not do with separate calls. They exist so the writes succeed or fail together (D5).
- `revoke all on function … from public, anon, authenticated, service_role`, then `grant execute … to authenticated`.
- Payloads are **database-shaped** (the frontend parses and reviews the document; §5). The functions check the payload's structure, then rely on the existing constraints, guards, and triggers for the values.
- Check, not-null, and invalid-value errors from inner writes are re-raised as `import_values_invalid` (`22023`). Known errors from the inner functions and triggers (`character_active_exists`, `character_campaign_unavailable`, `item_limit_reached`, `currency_limit_exceeded`, `currency_insufficient`, …) pass through unchanged.
- Both RPCs take `p_source_label text default null`: trimmed, empty becomes null, otherwise 1–120 characters with no control characters (`import_source_invalid`, `22023`). The dialog prefills it with the uploaded file's name, or leaves it empty for pasted text.

### 3.3 `public.character_imports` (provenance, D10)

```text
character_imports
  id uuid pk default gen_random_uuid()
  character_id uuid not null → characters(id) on delete cascade
  imported_by uuid not null → profiles(id) on delete cascade
  kind text not null check (kind in ('new', 'update'))
  source_label text null check (trimmed, 1–120 characters, no control characters)
  change_count integer not null check (change_count >= 0)
  imported_at timestamptz not null default now()
  index (character_id, imported_at desc)
```

- RLS enabled; `revoke all … from public, anon, authenticated, service_role`; `grant select … to authenticated` only. Clients have **no** insert, update, or delete privilege, so the record cannot be edited, forged, or removed; it goes away only with its character.
- Read policy: the same rule as the sheet (`exists` a visible `characters` row where the caller is the owner or `sheet_visibility = 'campaign'`), so the history is exactly as private as the sheet.
- Writes go only through `private.record_character_import(p_character_id uuid, p_kind text, p_source_label text, p_change_count integer)`: SECURITY DEFINER, `set search_path = ''`, `EXECUTE` for `authenticated` (the `private` schema is not exposed through the API, so clients cannot call it directly). It re-checks that the caller owns the character and is a current member, then inserts with `imported_by = auth.uid()`. The two RPCs call it as their last step, so a failed import records nothing.
- `change_count`: for `new`, 1 for the character plus the number of items and 1 if coins were added; for `update`, the number of selected changes applied.
- Retention is bounded by the character: no trimming is planned. At most one row per successful import.

### 3.4 `public.import_character(p_campaign_id uuid, p_character jsonb, p_source_label text default null) returns uuid`

Payload:

```json
{
  "details": { "name": "…", "species": null, "class_name": "…", "subclass": null, "background": null, "level": 3 },
  "vitals": { "max_hp": 24, "current_hp": 24, "temp_hp": 0, "armor_class": 15, "speed": 30 },
  "sheet": { "version": 1, "abilities": {}, "…": "…" },
  "items": [{ "name": "Rope", "quantity": 1, "weight": 10, "description": null, "equipped": false, "attuned": false }],
  "coins": { "cp": 0, "sp": 4, "gp": 12 }
}
```

Steps, in one transaction:

1. Check that `p_character` is an object with the expected keys and types, and that `items` has at most 200 entries (`import_invalid`, `22023`, otherwise).
2. `public.create_character(p_campaign_id, details…, p_in_party => false)`. This checks membership, locks the campaign, applies the one-active rule, and creates the empty sheet.
3. `update public.character_sheets set max_hp, current_hp, temp_hp, armor_class, speed, sheet … where character_id = <new id>`.
4. `insert into public.character_items (character_id, name, quantity, weight, description, equipped, attuned) select … from jsonb_to_recordset(items)`. The cap trigger still runs.
5. If any coin is non-zero, `perform public.adjust_character_currency(<new id>, cp, sp, gp)`. This writes one coin-log row.
6. `perform private.record_character_import(<new id>, 'new', p_source_label, <count>)`.
7. Return the new id.

Any failure rolls everything back, so a failed import never leaves a partial character or a provenance row.

### 3.5 `public.apply_character_update(p_character_id uuid, p_expected jsonb, p_changes jsonb, p_source_label text default null) returns timestamptz`

`p_expected` carries the versions the review was built from:

```json
{ "character_updated_at": "…", "sheet_updated_at": "…", "items": { "<item id>": "<updated_at>" } }
```

`p_changes` carries only what the owner selected, already merged into database shape by the frontend:

```json
{
  "details": { "level": 4, "subclass": null },
  "vitals": { "max_hp": 31, "current_hp": 31 },
  "sheet": { "version": 1, "…": "the complete new body" },
  "items": { "add": [ … ], "update": [{ "id": "…", "quantity": 2 }], "remove": ["…"] },
  "coins": { "cp": 0, "sp": 4, "gp": 20 }
}
```

Steps, in one transaction:

1. Lock the character: `select … from public.characters where id = p_character_id and owner_id = auth.uid() for update`. No row (unknown, not visible, not the owner, departed) raises `character_unavailable` (`P0001`). The row lock serializes with the departure hook and with status changes.
2. Lock the sheet `for update`. If `characters.updated_at` or `character_sheets.updated_at` differs from `p_expected`, raise `import_conflict` (`P0001`).
3. If `details` is present, update only those columns on `characters`.
4. If `vitals` or `sheet` is present, update them on `character_sheets`. The body is a full replacement computed from the reviewed current body, which is safe because step 2 proved it is unchanged.
5. Items: each `remove` deletes `where id = … and character_id = p_character_id and updated_at = <expected>`; each `update` does the same filtered update; zero rows raises `import_conflict`. Then `add` inserts. An id that belongs to another character therefore matches nothing and fails.
6. If `coins` is present, compute the deltas from the balances read under the step-2 lock and `perform public.adjust_character_currency(...)` when any delta is non-zero.
7. `perform private.record_character_import(p_character_id, 'update', p_source_label, <number of changes>)`.
8. Return the sheet's final `updated_at`.

Status, `in_party`, `sheet_visibility`, and `portrait_path` are not accepted keys (D8); their presence fails with `import_invalid`. An empty `p_changes` (nothing selected) also fails with `import_invalid`; the Apply button is disabled in that state.

### 3.6 Errors and frontend copy

| Code | When | Copy |
| --- | --- | --- |
| `import_invalid` | The payload has the wrong shape (a frontend bug or a crafted call) | "This import couldn't be read. Check the file and try again." |
| `import_values_invalid` | A value failed a database rule the frontend missed | "Some values in this import aren't allowed. Review them and try again." |
| `import_source_invalid` | The source label is too long or has control characters | "Use a source label of up to 120 characters." |
| `import_conflict` | The character changed after the review was loaded | "This character changed while you were reviewing. The latest version has been loaded; review the update again." |
| `character_active_exists` | Import as new while an active character exists | "You already have an active character here. Use Import updates on that character, or retire them first." |
| Existing codes | Membership, caps, coin limits | The existing `characterErrors` and inventory copy. |

## 4. Authorization and concurrency

### 4.1 Matrix

| Action | Anon | Non-member | Member | Campaign owner | Character owner (member) | Departed owner |
| --- | --- | --- | --- | --- | --- | --- |
| Import as new character | — | — | yes, as their own | yes, as their own | — | — |
| Apply an update | — | — | — | **—** for others' characters | yes | — |
| Copy the update prompt (reads the sheet) | — | — | only if the sheet is shared, and only the conversion prompt is offered | same as member | yes | — |
| Markdown export | — | — | if the sheet is shared | if the sheet is shared | yes | — |
| Read import history | — | — | if the sheet is shared | if the sheet is shared | yes | — |
| Write, edit, or delete import history | — | — | — | — | only through the two RPCs; never edit or delete | — |

Export and the update prompt only read data the viewer can already read. Neither needs a database change. Only the owner sees **Import updates**.

### 4.2 Why SECURITY INVOKER

A SECURITY DEFINER import would need to re-implement every ownership, membership, and visibility check. Running as the caller means the existing column grants, RLS policies, guard trigger, cap trigger, and check constraints decide every write, exactly as they do for the sheet editor. The inner calls that are SECURITY DEFINER (`create_character`, `adjust_character_currency`, `private.record_character_import`) each do their own membership and ownership checks. The provenance helper is the only write path into `character_imports`, which is why that one step is SECURITY DEFINER while the rest are not.

### 4.3 Concurrency

- **New character:** `create_character` locks the campaign `FOR SHARE`, which serializes with leaving and removal.
- **Update:** the character row lock serializes with departure and status changes; the sheet row lock plus the `updated_at` comparison covers the body, vitals, and coins (every coin change moves it, M3 §5.3); per-item `updated_at` filters cover items. Any mismatch fails the whole apply, and the frontend reloads the character and rebuilds the review with no changes selected.
- Item ids that were removed on another device fail the same way.

### 5.2 Validation layers

1. **Parse:** JSON, size, format, and version.
2. **Strict document validation:** types and bounds per field, reported per field in review. This is stricter than `normalizeSheet`, which clamps silently; an import must show what is wrong rather than trim it.
3. **Normalize:** after review, the accepted values go through the existing `normalizeSheet`, `toCharacterDetails`, `validateVitals`, and `normalizeItemInput`, so imported rows are identical in shape to hand-entered ones.
4. **Database:** constraints, guards, and triggers, as for every other write.

### 5.3 Integration

- **Tent (`CharacterTent.tsx`):** an **Import character** action next to creating one. If the player already has an active character in the campaign, the action explains D7 and links to that character's **Import updates**, without opening the dialog.
- **Source label:** both dialogs have an optional "Source" field (up to 120 characters), prefilled with the uploaded file's name and editable, stored as the provenance label (D10).
- **Sheet (`CharacterSheet.tsx`):** for the owner, **Import updates** and **Export Markdown**. For other members viewing a shared sheet, **Export Markdown** only. Both are disabled while the sheet has unsaved edits ("Save or cancel your edits first"), the same rule the legacy app used.
- After a successful new import, the tent opens the new character's sheet. After an update, the sheet shows the updated values and a success message naming how many changes were applied.
- Loading, empty (nothing pasted), parse-error, review, saving, conflict, and success states are all explicit. Cancelling or leaving the dialog saves nothing; leaving with a pasted, unapplied document goes through `UnsavedChangesDialog`.

### 5.4 Accessibility

The dialogs use the existing dialog patterns: focus moves to the heading, errors are linked to their fields, the change list is a list of labelled checkboxes, and the copy buttons announce "Copied".

## 6. Membership, lifecycle, and retention

- Importing requires current membership (via `create_character` and the RLS policies). A departed player cannot import or apply updates; their characters are unchanged.
- A new character is not in the party, so importing never changes what other members see in the Party panel until the owner adds it.
- Imported coins appear in the coin log like any other change (D11). Deleting the character or campaign removes everything, including its import history, as today.
- Import history follows the sheet's visibility: it disappears for other members when the owner makes the sheet private or leaves, and returns on rejoin, like the sheet. An `imported_by` account deleted later takes its rows with it (`on delete cascade`), matching how that account's characters already go.

## 7. Migration strategy

- Two forward-only migrations, each wrapped in `begin; … commit;`:
  1. `add_attack_ids` (§3.1): the attack-id backfill, the replaced validator, and the in-migration verification. This is the only change to existing data and to an existing function. It keeps every attack and every other key, and only adds ids.
  2. `add_character_imports`: `character_imports` (RLS enabled, revoke all, select-only grant, one read policy), `private.record_character_import`, and the two RPCs, each with explicit `revoke` and `grant`. No existing object changes, and no backfill is needed (no imports exist yet).
- **Pre-flight (read-only):** list the existing functions and the counts of `characters`, `character_sheets`, `character_items`, and `character_currency_log`; the number of sheets with attacks and the total number of attacks; and the largest `octet_length(sheet::text)` plus 45 bytes per attack on that sheet, which must stay under 65,536.
- **Apply:** `npm run db:migrate` (never `db:reset`), then `npm run db:types`.
- **Post-checks (read-only):** the number of sheets with attacks and the total number of attacks are unchanged; every attack has a UUID `id`, unique within its sheet; every sheet passes `private.character_sheet_is_valid`; `character_imports` has RLS enabled, one SELECT policy, and only `SELECT` for `authenticated`; the two RPCs have `prosecdef = false` and the helper `prosecdef = true`, each with `EXECUTE` only for `authenticated`; the existing row counts are unchanged.
- **Rollback:** a compensating migration that drops the two RPCs, the helper, and the table. Dropping the table discards the recorded import history; the characters themselves are unaffected. For attack ids, a compensating migration restores the previous validator; the ids can stay in the data, because the old validator accepts any keys on an attack object.

## 8. Testing

### 8.1 Integration — `e2e/local-supabase-imports.spec.ts` (new, added to `test:local-supabase`)

New character:

- An import creates the character, sheet, items, and coins; the character is active, not in the party, private, with no portrait; one coin-log row is written.
- A non-member and an anonymous client are denied, and nothing is created.
- With an existing active character, the import fails with `character_active_exists` and nothing is created.
- 201 items, an invalid sheet body, or an out-of-range vital rolls back the whole import: no character row remains.
- Status, `in_party`, `sheet_visibility`, or `portrait_path` in the payload is rejected.

Update:

- The owner applies details, vitals, body, item add, update, and remove, and coins in one call; every value changes and one coin-log row is written.
- Another member, the campaign owner (for a member's character), a departed owner, and a non-member are denied with `character_unavailable`.
- A stale `character_updated_at`, `sheet_updated_at`, or item `updated_at` (including a coin change from another client after the review was loaded) fails with `import_conflict`, and **no** part of the update is applied.
- An item id belonging to another character fails and changes nothing.
- Visibility, party membership, status, and the portrait are unchanged afterwards.

Attack ids:

- A sheet save with an attack missing its `id`, with a non-UUID `id`, or with two attacks sharing an `id` is rejected by the check constraint; a save with valid ids succeeds.
- The backfill is checked by the post-checks (§7) rather than a test, because tests create their own sheets after the migration.

Provenance:

- A successful new import and a successful update each write exactly one `character_imports` row with the right kind, label, count, and `imported_by`; a failed or conflicting import writes none.
- A label over 120 characters fails with `import_source_invalid` and nothing is written.
- The owner reads the history; another member reads it only while the sheet is shared; a non-member, a departed member, and the campaign owner (for a private sheet) read nothing.
- Direct `insert`, `update`, and `delete` on `character_imports` are denied for every account, including the owner.
- Deleting the character removes its history.

Tests create their own accounts and campaigns and delete them in `finally`. Counts are scoped to the test's own campaigns.

## 10. Acceptance criteria

- A player can turn a Markdown sheet into a new character using only the copied prompt, an outside assistant, and a paste, and sees every value before anything is saved.
- A failed import never leaves a partial character.
- An update shows each proposed change with its current value, applies only the selected ones, and applies nothing if the character changed during review.
- No import changes visibility, party membership, status, the portrait, ownership, or campaign.
- Nobody but the character's owner can apply an update, including the campaign owner.
- Markdown export works for the owner and for members who can read a shared sheet.
- Every successful import leaves exactly one provenance row, readable exactly where the sheet is, and no account can write, edit, or delete provenance directly.
- All §8.5 commands pass.

## 12. Risks and edge cases

### Risks

| # | Risk | Mitigation |
| --- | --- | --- |
| R1 | An outside assistant returns malformed or invented values. | Strict validation, a full review before saving, and changes unselected by default for updates. |
| R2 | A handoff contains instructions aimed at the assistant. | The prompts tell the assistant to treat the source as data; the app treats every value as plain text and never acts on content. |
| R3 | The attack-id migration touches every existing sheet with attacks, and an editor that drops ids would break saves. | It only adds ids and verifies every row before committing (§3.1); the frontend change ships in the same phase; the old validator can be restored without removing the ids. |
| R4 | Coin-log rows from imports are not labelled as imports. | Accepted (D11). The `character_imports` row at the same time records that an import happened. |
| R5 | Updating a character from a stale prompt copy. | The apply compares versions; the review also shows current values, so an old prompt's changes are visible as such. |

### Edge cases covered

- An empty document, an empty inventory, and zero coins.
- Current HP above a newly imported max HP (rejected in review and by the check constraint).
- A retired or deceased character can receive updates (M2 R2), but import as new always creates an active character.
- Removing an item or attack and also updating it in the same update (blocked as a conflicting pair in `resolveUpdate`).
- Two attacks with the same name: they have different ids, so an update targets the right one.

### Resolved questions

1. Should a character import record its own provenance? **Yes** (D10, §3.3).
2. Should the coin log gain a `source` column? **No** (D11).
