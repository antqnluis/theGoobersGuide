### M5 assertions changed (`e2e/local-supabase-adventures.spec.ts`)

1. **Catalog test:** `delete_orphaned_adventure` became `after_adventure_participant_delete`; the update policy is "Writers edit their adventures"; the trigger lists now include the reconcile and consent triggers; the departure hook now touches participants (it used to be asserted as unchanged).
2. **Visibility check:** `'party'` is now a valid value (it fails `adventures_visibility_matches_type` on a main adventure instead); `'everyone'` takes its place as the invalid value.
3. **Keys and visibility:** a visibility change is no longer `adventure_reassignment_forbidden`; it is `adventure_visibility_forbidden` (D6), tested for four value and adventure combinations.
4. **Participants:** the foreign-key tests insert as `proposed` (a second `accepted` row is refused by the new guard), and the owner-mismatch case uses a second adventure, since b2 already has a live row in the first (D1).
5. **D5 and D7 tests:** the second participant joins through `proposed → invited → accepted`, and every row count is scoped to the test's campaign, so the leftover adventure from Phase 0 no longer shifts them.

Two archiving assertions the plan expected to change (archived adventures hidden from everyone but the creator) did not need to: those M5 tests archive a main adventure or check non-participants. The archived-participant read is covered by the new spec.

### Deviations from the plan

1. **Timestamp.** The system clock (14:16 UTC) is earlier than `20261116160128`, so the migration is named `20261116170000` to keep the order.
2. **`derived_adventure_visibility(p_adventure_id, p_archived)`** takes the archive state as a second argument. In a before-update trigger the table still holds the old row, so the new row's state has to be passed in. It is volatile, so it sees rows written earlier in the same command.
3. **Lock helpers.** `private.lock_adventure_campaign(uuid)` and `private.lock_adventure_row(uuid)` carry the campaign-then-adventure lock order for every RPC; characters are locked between them where one is involved (D14). Postgres-only, like the other internal functions.
4. **`private.after_adventure_archive_change()`** is the function behind the after-update archive trigger (§2.5 said "an after-update trigger").
5. **Archiving clears consent in `reconcile_adventure` itself,** including a partial request that never became a share, so restoring never lets one more consent publish the thread (the plan only said so for a share that ends).
6. **A derived visibility change keeps `updated_by`.** It is not an edit by whoever triggered it (for example, the campaign owner removing a member). `updated_at` still advances, as the plan says.
7. **One active character per player.** The characters table allows one active character per player per campaign, so a player's "second character" can only be a retired one, which D2 already excludes. The "own second character" test retires the first character (which stays in the thread) and creates a new one; the D1 index is also exercised directly in the database test with a retired character.
8. **Inserts and transitions are guarded for every caller,** as the plan says. Test fixtures that need a second accepted participant now go through `proposed → invited → accepted`.

### Not done here (planned later)

Generated types (Phase 2); the UI test, `DATABASE_SCHEMA.md`, and the M03 audit, M03.1, and M03.5 note updates (Phase 5). The departure hook's comment is rewritten in the migration.

### Decisions and deviations

1. **`groupAdventures` changed shape now,** not in Phase 3: it returns six groups. The board still renders only the four it knew, so party-shared adventures and the "Waiting for you" group are computed but not shown until Phases 3 and 4.
2. **`stale` result.** The plan names only the error codes; actions return `{ ok: false, reason: 'stale' }` for the two stale-state codes, so surfaces can tell "refreshed" from "failed".
3. **`participantLabel`** takes `(participant, adventure, userId, roster)` and returns null for an accepted participant. "Invited by Mira" is a separate `inviterLabel`, because list rows do not carry `invited_by`.
4. **`respond` takes the invitation** (participant and adventure ids) so a failure can drop or refresh the right adventure.
5. **Invited-character copy.** `adventure_character_unavailable` has two meanings (M5's own character; M6's someone else's). `propose` uses `inviteError` for the M6 copy; creating an adventure still shows the M5 copy.

## Phase 3 — Participants and invitations UI (2026-11-16) — done

No migration or database change. The board and the adventure page now show collaboration; sharing and the party's read-only view are Phase 4.

- **`AdventureParticipants`** (new, in `AdventureView` for personal and side adventures): accepted characters with their players and a "Agrees to share with the party" mark; pending, declined, and left rows in words (`participantLabel`), after the accepted ones. An accepted participant approves, rejects, withdraws, invites a character (a native `select` of `invitableCharacters`, then a confirmation naming who must approve, or saying the invitation goes out right away for a sole participant), invites a declined or left character again, and leaves. Everyone else, and an archived adventure, read only. The last accepted participant is not offered Leave. Ten live participations show the limit text instead of the picker.
- **`AdventureInvitationCard`** (new): title, type, the invited character, the inviter, and when. A shared adventure adds an unticked "Keep it shared with the party" box with the line that leaving it unticked makes the adventure private for everyone. Decline asks first.
- **Board (`CampAdventures`):** a "Waiting for you" group first, with invitation cards, then adventures with a proposal to approve ("Approve Bram joining") or a share request ("Mira wants to share this with the party"). The filter covers invitations. An invitations error shows a retry in that group and leaves the adventures alone. Accepting opens the adventure; declining, leaving, and proposing each post a notice.
- **Places count:** `CampaignCamp` takes `waiting` (counts by destination). The Adventures entry reads "Adventures (2)" and is named "Adventures, 2 waiting" while the count is above zero. The workspace reads `count_my_adventure_requests` once the campaign loads and on focus; opening the destination refreshes the list, invitations, and count.
- **`AdventureView`:** `canEdit` replaces "not archived" for edit controls; the audience chip reads "Every member", "The party", "Only the people in it", or "Only you".
- **Mocks and browser spec:** `mockAdventures` gains participant rows, invitations, the characters count's two reads, and the eight RPCs in miniature; `e2e/adventures.spec.ts` gains six flows (an invitation, decline, the Places count, propose, approve and withdraw, leave). Written and listed with `playwright test --list` (16 tests), not run.

### Decisions and deviations

1. **A visible character list only.** The invite picker offers characters the viewer can read (their own, shared, or in-party ones the app lists). D2 allows any active character of another member, but a player's private character is not readable by others, so it cannot be named in the picker. A player with no visible active character cannot be invited from the picker.
2. **Controls stay in place while confirming:** the opening controls are disabled, not hidden, so focus returns to the control that opened the confirmation. If that control is gone (a rejected row) or disabled, focus goes to the Participants heading.
3. **"Approve Bram joining"** does not say who proposed: list rows do not carry `invited_by`. The adventure page shows the proposal.
4. **Notice wording:** proposing says "Invitation proposed." whether it was sent at once or waits for approval, because the client cannot tell without another read.
5. **`CampaignCamp.waiting`** is a generic map by destination, though only Adventures uses it.
