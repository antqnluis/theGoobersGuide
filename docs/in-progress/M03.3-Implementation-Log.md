### Deviations from the plan

1. **Weight above the bound reports `22003`, not `23514`.** Plan §9.1 expects weight 100,000 to fail with `23514`. The column is `numeric(7, 2)`, which cannot hold 100,000 at all, so PostgreSQL raises `numeric field overflow` (`22003`) before the check runs. The bound is enforced either way (99,999.99 is accepted, 100,000 and 99,999.999 are refused); `character_items_weight_check` still covers negatives. The tests assert `22003` for the upper bound. Frontend validation (Phase 3) enforces 0–99,999.99 with field messages, so users never see this code.
2. **Test-data safety.** The first draft of the currency-check test updated `character_sheets` without a `where`, which touched the real sheet inside a rolled-back transaction. It is now scoped to the fixture character, and the real sheet was verified unchanged afterwards.
3. **Migration timestamp** is the real creation time (`20261114190000`); the plan's `…160000` was illustrative.
4. `src/types/database.ts` is not regenerated yet. That is Phase 3.

### Deviations from the plan

1. **Membership is re-checked after the campaign lock, in its own statement.** Plan §4.1 step 3 locks the campaign `for share` "where the caller is a current member". With the membership test inside the locking statement, a removal that commits while the call waits for the lock would still be seen as a member (the statement's snapshot predates the removal). The RPCs lock first, then check membership in a fresh statement, so a call that lost the race returns `character_unavailable` or `item_unavailable`. The existing character RPCs use the single-statement form; they are unchanged.
2. **Test isolation.** The first Phase 1 draft counted and updated `character_items` rows without scoping them to the fixture character. With parallel workers this failed under `--repeat-each` (rows committed by another test were counted). All fixture queries are now scoped to the fixture character, and the spec passes repeatedly.

### Deviations from the plan

1. **Membership hooks now cover the items key.** As the plan anticipated (§6.3), `useCampaignMembership` uses exact, campaign-scoped keys, so the items key (`['campaigns','characters','items',characterId,userId]`) was not covered. Leave now marks the whole `characterItemsPrefix` stale without refetching, and removal invalidates it. The test asserts both. The existing sheet key has the same gap today; it is unchanged.
2. **One action for equip and attune.** The plan lists `item-equip`; both toggles share one action named `item-flag` (`changeItemFlag(characterId, itemId, 'equipped' | 'attuned', value)`), since they are the same single-column write.
3. **Quantity refreshes before reporting success.** Plan §6.3 says item caches are refreshed in the background. For quantity deltas the hook awaits the refetch, because the new `updated_at` is what an open edit form saves against, and a background refresh would let a quick edit after `+`/`−` report a false `item_conflict`. Add, edit, flag, and delete write the returned row (which carries its own `updated_at`) and refresh in the background as planned.
4. **Weight text rules.** The form accepts `.5` but rejects `7.` (a trailing dot), in addition to the planned bounds.
5. **`e2e/support/campMocks.ts` is unchanged.** Its sheet mocks do not return the purse columns yet; the mocks are extended in Phase 4 with the UI.
