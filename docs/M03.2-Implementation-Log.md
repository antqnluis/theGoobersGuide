### Deviations from the plan

1. **`private.character_sheet_is_valid` is executable by `authenticated`.** Plan §2.2 says EXECUTE is revoked from everyone because "check constraints do not need it". PostgreSQL does check EXECUTE on functions used in CHECK constraints against the writing role: an owner updating their vitals failed with `permission denied for function character_sheet_is_valid`. The function is pure (reads no tables, no data), so a narrow `grant execute … to authenticated` was added in a second migration (migration 1 was already applied). `anon`, `public`, and `service_role` remain without access; the guard trigger and the departure hook remain postgres-only. The privilege test asserts exactly this.
2. **Migration timestamps** use the real creation date (`20261113…`) instead of the plan's illustrative `20261114…` (plan §9.1 allows this).
3. **Sheet validator also type-checks the free-text fields** (`features`, `spells`, `notes`, `alignment` must be strings; `experience` must be null or an integer 0–1,000,000; `saving_throws` must be unique). These are within "structural rules" of plan §5.2 and match the v1 type.

### Notes and deviations

1. **`create` resolves to `boolean`** like every other action (plan §8.1); the workspace finds the new character from the refetched list.
2. **Client-side size cap is 60,000 bytes**, not 65,536: the database measures `jsonb::text`, which adds spaces after `:` and `,`, so the client stays below the real limit.
3. **Attack field limits** (name 80, bonus 20, damage 60, notes 200 characters) are client-only; the plan left per-field limits to the frontend.
4. **Extra internal error codes** (`character_update_denied`, `character_delete_denied`, `sheet_unavailable`, `sheet_conflict`) are thrown client-side when a write matches no row, and map to the copy in plan §4.3/§5.4.
5. The generated RPC types omit `null` for optional arguments, so the service sends `undefined` for unset optionals; PostgREST then applies the function defaults (`null`).
