## Overview and objectives

M4 gives each campaign a notebook. A player can keep a private note that no one else can read, including the campaign owner, or share one with the campaign so every current member can read and edit it. Notes live at the **Journal crates**, which today are unlabeled scenery in the camp.

M4 delivers:

1. **A `public.notes` table** with RLS: private notes for their author only, campaign notes for every current member. It has explicit grants, a guard trigger that keeps keys fixed and allows only the author to change visibility, an edit record (`updated_by`), and a per-author cap.
2. **No new RPCs.** Every write is a single-row direct write covered by RLS, the checks, and the guard trigger, the same reasoning as item writes in M03.3 §3.1.
3. **Optimistic concurrency** for every note save (`.eq('updated_at', previous)`), so two people editing a shared note never silently overwrite each other.
4. **A Notes destination at the Journal crates**: a list (shared and private), an editor, a visibility toggle for the author, an optional link to a character, delete for the author, and an unsaved-changes guard.
5. **Updated copy** for deleting a campaign, because it now also removes notes.
6. **Tests**: multi-account integration tests against the local stack (including attempts to bypass the frontend), unit tests, and mocked and real-stack browser tests.

## 2. Database schema, constraints, and relationships

### 2.1 `public.notes`

```sql
create table public.notes (
  id uuid primary key default gen_random_uuid(),
  campaign_id uuid not null references public.campaigns (id) on delete cascade,
  author_id uuid not null default auth.uid() references public.profiles (id) on delete cascade,
  visibility text not null default 'private',
  title text not null,
  body text not null default '',
  character_id uuid,
  updated_by uuid references public.profiles (id) on delete set null,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),

  constraint notes_visibility_check check (visibility in ('private', 'campaign')),
  constraint notes_title_check check (
    title = btrim(title) and char_length(title) between 1 and 120 and title !~ '[[:cntrl:]]'
  ),
  -- Newlines and tabs are allowed in the body; other control characters are not.
  constraint notes_body_check check (
    char_length(body) <= 20000 and body !~ '[\x01-\x08\x0B\x0C\x0E-\x1F\x7F]'
  ),
  constraint notes_character_fkey foreign key (character_id, campaign_id)
    references public.characters (id, campaign_id) on delete set null (character_id)
);

create index notes_campaign_updated_idx on public.notes (campaign_id, updated_at desc);
create index notes_author_idx on public.notes (author_id, campaign_id);
create index notes_character_idx on public.notes (character_id) where character_id is not null;
```

- `author_id` defaults to the caller and has no insert grant, so a client can never write a note as someone else.
- A composite FK with `match simple` is skipped when `character_id` is null, so unlinked notes need no character. The guard (§2.2) checks a new link before the FK does, so a client sees `note_character_unavailable` rather than `23503`. The FK is the backstop for every path.
- `on delete set null (character_id)` clears only the link and keeps `campaign_id`.

### 2.2 Guard trigger (every write path)

```sql
create function private.guard_note_write()
returns trigger
language plpgsql
security definer set search_path = ''
as $$
begin
  -- The FK's "set null" when a linked character is deleted runs inside another
  -- trigger. It only clears the link, so it is not recorded as an edit.
  if tg_op = 'UPDATE' and pg_trigger_depth() > 1 then
    return new;
  end if;

  if tg_op = 'UPDATE' then
    if new.id <> old.id or new.campaign_id <> old.campaign_id
       or new.author_id <> old.author_id or new.created_at <> old.created_at then
      raise integrity_constraint_violation using message = 'note_reassignment_forbidden';
    end if;
    if new.visibility <> old.visibility and auth.uid() is distinct from old.author_id then
      raise insufficient_privilege using message = 'note_visibility_author_only';
    end if;
  else
    -- INSERT: serialize one author's inserts in one campaign, then enforce the cap (D3).
    perform pg_advisory_xact_lock(
      hashtextextended('notes:' || new.campaign_id::text || ':' || new.author_id::text, 0)
    );
    if (select count(*) from public.notes
        where campaign_id = new.campaign_id and author_id = new.author_id) >= 500 then
      raise exception 'note_limit_reached';
    end if;
  end if;

  -- A new or changed link must point at a character a current member owns (D5).
  if new.character_id is not null
     and (tg_op = 'INSERT' or new.character_id is distinct from old.character_id)
     and not exists (
       select 1 from public.characters as c
       join public.campaign_members as m
         on m.campaign_id = c.campaign_id and m.profile_id = c.owner_id
       where c.id = new.character_id and c.campaign_id = new.campaign_id
     ) then
    raise exception 'note_character_unavailable';
  end if;

  new.updated_by := auth.uid();
  return new;
end;
$$;

revoke all on function private.guard_note_write() from public, anon, authenticated, service_role;

create trigger notes_guard_write
  before insert or update on public.notes
  for each row execute function private.guard_note_write();

create trigger notes_set_updated_at
  before update on public.notes
  for each row execute function private.set_updated_at();
```

- A nested update (an FK `set null` action) passes through untouched. When a linked character is deleted, the action changes only `character_id`, so `updated_by` stays (the character's owner never becomes the editor of a note they may not be able to read). When an editor's account is deleted, the action clears `updated_by`, as intended. An earlier draft of this branch restored `updated_by` and so blocked account deletion; Phase 1 fixed it (see the log). `set_updated_at` still advances `updated_at`, so an editor open on that note gets a conflict on the next save, which is correct because the link changed.
- The link check runs only when the link is new or changed, so editing a note whose linked character's owner has since left still works.
- The guard is SECURITY DEFINER, so the cap's count sees every row whatever the caller's RLS. It applies to `postgres` and `service_role` writes too. A visibility change from a path without an Auth identity (`auth.uid()` null) is refused, so a later import or admin path must act as the author.
- The advisory lock is transaction-scoped and keyed by campaign and author, so different authors never wait for each other.

### 2.3 Relationships and delete behaviour

| Event | Effect |
| --- | --- |
| Campaign deleted | Every note in it cascades, including departed authors' notes. |
| Author's account hard-deleted | Their notes cascade, private and shared (D2). Other authors' notes keep their content, and `updated_by` becomes null where the deleted account was the last editor. |
| Linked character deleted | The link is cleared. The note stays. |
| Leave or removal | Everything is kept. Reads and writes change through RLS (§3). |
| Rejoin | The author's private notes are readable and writable again. |
| Ownership transfer | No effect. |

```text
campaigns 1 ──< notes >── 1 profiles (author)
                  │
                  └── 0..1 characters (same campaign)
```

## 3. RLS policies and authorization matrix

### 3.1 Grants

```sql
alter table public.notes enable row level security;

revoke all on table public.notes from public, anon, authenticated, service_role;

grant select, delete on table public.notes to authenticated;
grant insert (campaign_id, visibility, title, body, character_id) on table public.notes to authenticated;
grant update (visibility, title, body, character_id) on table public.notes to authenticated;
```

`id`, `author_id`, `updated_by`, `created_at`, and `updated_at` are never client-written. `campaign_id` is insertable but not updatable.

### 3.2 Policies

```sql
-- Read: current members read shared notes; the author reads their own while a member.
create policy "Members read shared notes and authors read their own"
  on public.notes for select to authenticated
  using (
    campaign_id in (select private.current_campaign_ids())
    and (visibility = 'campaign' or author_id = (select auth.uid()))
  );

create policy "Members write their own notes"
  on public.notes for insert to authenticated
  with check (
    author_id = (select auth.uid())
    and campaign_id in (select private.current_campaign_ids())
  );

-- Update: any current member edits a shared note; the author edits their own.
create policy "Members edit shared notes and authors edit their own"
  on public.notes for update to authenticated
  using (
    campaign_id in (select private.current_campaign_ids())
    and (visibility = 'campaign' or author_id = (select auth.uid()))
  )
  with check (
    campaign_id in (select private.current_campaign_ids())
    and (visibility = 'campaign' or author_id = (select auth.uid()))
  );

create policy "Authors delete their notes"
  on public.notes for delete to authenticated
  using (
    author_id = (select auth.uid())
    and campaign_id in (select private.current_campaign_ids())
  );
```

- A departed author's shared notes stay readable and editable by current members, because the read and update policies check the reader's membership, not the author's (M03.1 §6.2).
- Making a note private is the author's own update, so the `with check` passes. A non-author who tries gets `note_visibility_author_only` from the guard before the check matters.

### 3.3 Authorization matrix

Key: **R** read, **C** create, **U** update, **D** delete, **—** denied (no rows, or `42501`). "Member" means a current member who is not the note's author. "Departed author" means the author after leaving or removal.

| Action | Anon | Non-member | Member | Campaign owner (not author) | Author | Departed author |
| --- | --- | --- | --- | --- | --- | --- |
| Read a private note | — | — | **—** | **—** | R | — |
| Read a campaign note | — | — | R | R | R | — |
| Create a note | — | — (RLS) | C own | C own | C own (up to 500) | — |
| Edit title, body, or link of a private note | — | — | — (0 rows) | — (0 rows) | U | — |
| Edit title, body, or link of a campaign note | — | — | U | U | U | — |
| Change visibility | — | — | `42501` | `42501` | yes | — |
| Delete | — | — | — (0 rows) | — (0 rows) | D | — |
| Move a note to another campaign or author | — | — | `42501` (no column grant), and the guard for every path | same | same | — |

**Explicit negatives to test:** the campaign owner cannot read, edit, or delete a member's private note, and cannot delete or change the visibility of a member's campaign note. A member cannot insert a note as someone else, set `author_id`, `updated_by`, `created_at`, or `updated_at`, move a note to another campaign, link a character from another campaign or a departed player's character, or exceed the cap. A departed player loses every read and write, including on their own shared notes, and gets them back on rejoining.

## 4. Workflows and requests

### 4.1 Direct writes

| Action | Request | Zero rows or error |
| --- | --- | --- |
| List | `select(noteListFields).eq('campaign_id', id).order('updated_at', { ascending: false })`. List fields omit `body`. | Error → retry state. |
| Open | `select(noteFields).eq('id', id).maybeSingle()` | No row → `note_unavailable`. |
| Create | `insert({ campaign_id, visibility, title, body, character_id }).select(noteFields).single()` | `42501` → "You can no longer add notes to this campaign." `note_limit_reached`, `note_character_unavailable` → their copy. |
| Save | `update({ title, body, character_id }).eq('id', id).eq('updated_at', previous).select(noteFields).maybeSingle()` | No row → re-read the note: found → `note_conflict` (D6), not found → `note_unavailable`. |
| Change visibility | `update({ visibility }).eq('id', id).eq('updated_at', previous).select(noteFields).maybeSingle()`, after the D9 confirmation when going private. | Same as Save. `note_visibility_author_only` → fallback copy (the button is author-only). |
| Delete | `delete().eq('id', id).select('id').maybeSingle()`, after a confirmation. | No row → `note_unavailable`, refetch the list. |

### 4.2 Concurrency

| Race | Outcome |
| --- | --- |
| Two members save the same shared note from the same version | The first wins. The second matches no row and gets `note_conflict` with their text kept (D6). |
| "Save mine anyway" after a conflict | Saves against the latest `updated_at`. Another conflict is possible and shown the same way. |
| The author makes a note private while a member edits it | The member's save matches no row and the re-read finds nothing → `note_unavailable`. The editor keeps their text so they can copy it, and the list refreshes. |
| The author deletes a note while a member edits it | Same as above. |
| A member edits while being removed | Removal first: the save matches no row (`note_unavailable`). Save first: the save is kept. |
| Five parallel inserts by one author at 499 notes | Exactly one succeeds, four get `note_limit_reached`. |
| A note is linked while the character is deleted | Delete first: the guard raises `note_character_unavailable`, or the FK fails (`23503`) and the client shows the generic copy. Link first: the delete clears the link. |

Invariants after any interleaving (asserted by tests): no author with more than 500 notes in a campaign, no note whose `character_id` belongs to another campaign, and no private note readable by anyone but its author.

### 4.3 Error copy (frontend)

| Message | Copy |
| --- | --- |
| `note_conflict` | "This note changed while you were editing. Your text is still here." With **Load latest** and **Save mine anyway**. |
| `note_unavailable` | "This note is no longer available. It may have been made private or deleted." |
| `note_limit_reached` | "You can keep up to 500 notes in a campaign. Delete one to add another." |
| `note_character_unavailable` | "That character is no longer in this campaign. Choose another or remove the link." |
| `note_visibility_author_only`, `note_reassignment_forbidden` | Fallback (programming errors) |
| `23514` | Field-level validation should have caught it. Fallback. |
| anything else | "We couldn't [load the notes / save this note / delete this note]. Check your connection and try again." |

- Leave marks `notesPrefix` stale with `refetchType: 'none'`. Remove refetches it, as the item and coin-log prefixes already do.
- A `note_unavailable` result removes the note's detail key and refetches the list.
- Deleting the campaign already invalidates the `['campaigns']` prefix, which covers notes.

### 6.4 Accessibility and layout

- Every async surface has loading, error with retry, empty, and success states. Focus moves to the title field when the editor opens, back to the note's row or "New note" on cancel or save, and to the confirm button when a confirmation opens. Errors use `role="alert"` and `aria-describedby`.
- Visibility is shown as text and an icon (`lock` for "Only you", `eye` for "Shared"), never by colour alone.
- Targets are at least 44 px. The page works at 390, 820, and 1440 px with no horizontal scroll (Playwright captures).

## 7. Membership departure, rejoin, and lifecycle

| Event | Private notes | Campaign notes |
| --- | --- | --- |
| Author leaves or is removed | Kept, invisible to everyone | Kept. Current members read and edit them, attributed to "A former member". No one can delete them or make them private (D1). |
| Author rejoins | Visible and editable again | The author's own again: delete and visibility return |
| Editor leaves | — | Kept. "Edited by A former member". |
| Ownership transfer | No change. The new owner gains nothing. | No change |
| Linked character's owner leaves | Link hidden, kept | Link hidden, kept |
| Author's account deleted | Cascade | Cascade (D2) |
| Campaign deleted | Cascade, with the updated confirmation | Cascade |

Copy change, **delete campaign**: "Delete **{campaign}** permanently? Its details, member list, notes, and every player's characters, character sheets, and inventories will be removed. This can't be undone." Phase 4 reconciles this with the current wording, which M03.8 may have extended.

## 8. Non-destructive migration strategy

### 8.1 Files (timestamp after `20261115221000`; use the real creation time)

| # | File | Contents |
| --- | --- | --- |
| 1 | `2026111?xxxxxx_add_notes.sql` | `notes` with constraints, indexes, guard and `updated_at` triggers, RLS, revokes, grants, and policies. |

Wrapped in `begin; … commit;`. It changes no existing table, policy, grant, function, or trigger. No backfill.

### 8.2 Pre-flight (read-only)

1. `git status` is clean, or contains M4 changes only.
2. `npm run supabase:status`. `schema_migrations` lists exactly the 22 versions ending `20261115221000`.
3. Baseline in a read-only transaction: row counts of `profiles`, `campaigns`, `campaign_members`, `campaign_invitations`, `characters`, `character_sheets`, `character_items`, `character_currency_log`, `character_imports`, `campaign_appearances`. The M1 ownership-consistency query (0 rows).
4. Optional local safety net outside the repo: `pg_dump` of `public` and `auth` data to the scratchpad.
5. Baseline suites: `npm run lint`, `npm run format:check`, `npm run build`, `npm test`, `npm run test:e2e`, `npm run test:local-supabase`.

### 8.3 Apply

`npm run db:migrate` (from `implementation/backend`). Then `npm run db:types` and `npx prettier --write src/types/database.ts`. Never run `db:reset`.

### 8.4 Post-migration checks (read-only)

| Check | Expected |
| --- | --- |
| Existing row counts | Identical to baseline (profiles may rise only from test accounts) |
| `relrowsecurity` on `notes` | true |
| `has_table_privilege` / `has_column_privilege` on `notes` | `authenticated`: select, delete, the listed insert and update columns. No insert on `author_id`, `updated_by`, `id`, `created_at`, `updated_at`. No update on `campaign_id`. `anon`, `service_role`, `public`: none. |
| `has_function_privilege` on `private.guard_note_write` | Nobody but `postgres` |
| Existing ACLs | Unchanged |

### 8.5 Rollback (compensating migration only)

Drop `notes` and `private.guard_note_write`. **This deletes every note.** It is only acceptable before real use. Otherwise export first.

### 8.6 Test-data safety

Integration tests create their own accounts and campaigns and delete their campaigns in `finally` (notes cascade). Counts are scoped to the test's own campaigns. Direct `postgres` writes run inside `begin; … rollback;` through `localDatabaseQuery`. Pre-existing rows are never touched.

## 9. Testing

### 9.1 Integration — `e2e/local-supabase-notes.spec.ts` (new)

Uses `e2e/support/localPlayers.ts`. Members join through the real invitation RPCs. Added to `test:local-supabase`.

**Catalog and privileges** (read-only): exactly as §8.4.

**Notes**
- The author creates a private note. `author_id` and `updated_by` are the author, `visibility = 'private'`, and `body` defaults to `''`.
- Edit, share, make private, and delete. Each returns the row, and `updated_at` advances.
- Checks: blank title, a title with surrounding spaces, a title over 120 characters, a control character, a body over 20,000 characters → `23514`. A body with newlines and tabs is accepted.
- The 501st note → `note_limit_reached`. Another author in the same campaign is unaffected.
- A save with a stale `updated_at` → 0 rows, row unchanged.
- Link a character in the campaign → accepted. A character from another campaign, a departed player's character, or a random UUID → `note_character_unavailable`. Deleting the linked character clears the link, keeps the note, and leaves `updated_by` unchanged.

**Visibility**
- Private: another member and **the campaign owner** read nothing (no row, and the note is absent from the list). Update and delete affect 0 rows.
- Shared: every current member reads and edits it. `updated_by` becomes the editor. Members other than the author get `note_visibility_author_only` on a visibility change and 0 rows on delete.
- Making it private hides it from members on the next read.

**Bypass attempts through the API** (publishable key, signed-in member)
- Insert with `author_id`, `updated_by`, `id`, or `created_at` set → `42501`.
- Insert into a campaign the caller is not in → `42501`.
- Update `campaign_id` → `42501`.

**Bypass attempts in the database** (as `postgres`, rolled back)
- Changing `campaign_id` or `author_id` → `note_reassignment_forbidden`.
- A visibility change with no Auth identity → `note_visibility_author_only`.
- The 501st note → `note_limit_reached`.

**Departure and rejoin**
- The author leaves: notes unchanged (`localDatabaseQuery`). The author reads and writes nothing. Members still read and edit the shared note, cannot delete it or make it private, and never see the private one. Removal behaves the same.
- Rejoin: the author reads and writes both again, and can delete the shared note.

**Cascades** (counts scoped to the test's campaigns)
- Deleting the campaign removes every note in it, including a departed author's.

**Concurrency** (`Promise.all` from separate clients)
- Two saves from the same version → exactly one row change, one 0-row result.
- Five parallel inserts at 499 notes → one success.
- A save racing `remove_campaign_member` → either applied or 0 rows, never any other error.
- After each: the §4.2 invariants hold (SQL assertions).

## 11. Acceptance criteria (M4 as a whole)

1. A member can create, edit, link, share, make private, and delete their own notes at the Journal crates, and every change persists across a reload.
2. A private note is readable only by its author while they are a member. The campaign owner has no override.
3. Every current member can read and edit a campaign note. Only its author can delete it or change its visibility, on every write path.
4. Two people saving the same note from the same version never overwrite each other silently, and the second keeps their text.
5. No one can write a note as someone else, move a note between campaigns or authors, link a character from another campaign, or exceed 500 notes per campaign.
6. Leaving or removal keeps every note. The departed author loses access, members keep shared notes, and rejoining restores the author's access.
7. Deleting a campaign removes its notes after a confirmation that says so.
8. Existing auth, campaigns, invitations, membership, characters, inventory, imports, appearances, and camp behaviour are unchanged, and their tests pass.
9. The migration ran with `db:migrate` only, existing row counts are unchanged, and no `db:reset` was run. All §9.4 commands pass and are reported.

## 12. Risks and edge cases

### Risks

| Risk | Mitigation |
| --- | --- |
| Without Realtime, members see a shared note's edits only on refetch | Refetch on window focus and when the destination opens. The conflict flow (D6) prevents lost work. Realtime is M7. |
| Departed authors' shared notes pile up with no one able to delete them (D1) | Members can still edit them. If it becomes a problem, D1's alternative is a small follow-up. |
| An author deleting their account removes shared notes others relied on (D2) | Matches the retention rule. The future account-deletion flow should warn about it. |
| Making a shared note private hides members' edits (D9) | Confirmation copy says so. Open editors keep their text on `note_unavailable`. |
| The client's bounds drift from the database checks | One source of limits in `noteValidation.ts`, mirrored by the SQL. The integration tests send every boundary. |
| The fifth destination crowds the scene at phone width | The crates are at the right of the panorama, away from the other plates. Phase 3 checks plates and hit targets with captures at 390 px. |
| "Notes" is also a section of the character sheet (D8) | Different place and page title. The camp page is titled "Campaign notes". |

### Edge cases covered

- An empty body is allowed; a note can be just a title.
- A title of only spaces is refused in the form and by the check.
- A double-submitted create makes two notes. The submit button is disabled while pending, and the second is easy to delete.
- A linked character retired or marked deceased stays linked (status does not matter).
- A note open in the editor is deleted or made private elsewhere → `note_unavailable`, text kept, list refreshed.
- A removed member with the journal open → the next save or refetch returns nothing, and the camp's existing "campaign not available" handling takes over.
