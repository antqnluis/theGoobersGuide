## 1. Overview and objectives

Membership is currently a one-way door: a player who joins can never leave, an owner cannot remove anyone, and ownership can never change hands. Deleting an owner's account silently deletes the campaign for every member. M1 closes these gaps before any player-owned data (M2 characters, M4 notes, M5/M6 adventures) exists, so later milestones inherit well-defined departure, rejoin, and ownership semantics.

M1 delivers:

1. **Hardened default privileges**: new objects that `postgres` creates in `public` are no longer automatically reachable by `anon`, `authenticated`, or `service_role`, and new functions are no longer executable by `PUBLIC`.
2. **Owner account deletion protection**: an account that owns campaigns cannot be deleted until ownership is transferred or the campaign is deliberately deleted.
3. **Ownership integrity**: a database-level invariant guarantees that `campaigns.owner_id` and the single `role = 'owner'` membership row always agree at commit.
4. **Three membership RPCs**: `leave_campaign`, `remove_campaign_member`, and `transfer_campaign_ownership`, all atomic, serialized per campaign, and authorized in PostgreSQL.
5. **A departure hook** (`private.handle_campaign_member_departure`), the single place where later milestones attach departure side effects.
6. **Frontend flows** in the existing Party panel (leave, remove) and Campaign settings panel (transfer), with confirmation, pending, success, and error states.
7. **Generated database types** for the new RPCs.
8. **Tests**: real multi-account integration tests against the local stack, unit tests, and mocked browser e2e tests.

Out of scope: characters, notes, adventures, Storage, Realtime, an account-deletion UI, invitation expiry, membership history tables, and any UI redesign. Display names and `get_campaign_party` ship in M1 as Phase 7 (§12, decision D5, reversed on request).

## 4. Database and migration specifications

### 4.1 Rules for every M1 migration

- New file under `implementation/backend/supabase/migrations/`, timestamp after `20261112140000` (use the actual creation time; the names below assume 2026-11-13), wrapped in `begin; … commit;`.
- No `drop table`, no `truncate`, no data rewrites. The only change to an existing object is the `campaigns_owner_id_fkey` delete action.
- Every new function: `set search_path = ''`, schema-qualified references, `revoke all … from public, anon, authenticated, service_role`, then explicit grants.
- Fail closed: a precondition that does not hold raises an exception, which aborts the migration without changing anything.
- Apply only with `npm run db:migrate` (`supabase migration up --local`). Never `db:reset`.

### 4.2 Migration 1 — `20261113100000_harden_default_privileges.sql`

Purpose: stop new objects created by `postgres` from being auto-exposed. This is the SQL equivalent of the Data API "automatically expose new tables" toggle and is version-controlled, so it applies identically to every local stack and, later, to any hosted project.

```sql
begin;

-- Objects postgres creates in public are no longer granted to the API roles.
alter default privileges for role postgres in schema public
  revoke all on tables from anon, authenticated, service_role;
alter default privileges for role postgres in schema public
  revoke all on sequences from anon, authenticated, service_role;
alter default privileges for role postgres in schema public
  revoke all on functions from anon, authenticated, service_role;

-- PostgreSQL grants EXECUTE on new functions to PUBLIC unless the creator's
-- global default says otherwise. This covers public and private alike.
alter default privileges for role postgres
  revoke execute on functions from public;

commit;
```

Notes:

- Default privileges affect **only objects created later**. Existing grants are untouched, so current tables, RPCs, auth, and invitations keep working.
- Trigger functions do not need EXECUTE for the role that fires the trigger, so existing and future triggers keep working (the existing `set_updated_at` is already revoked from `authenticated` and fires on their updates).
- `supabase_admin`'s defaults in `public` cannot be changed by `postgres` (Supabase KB: "Can't change the default privileges of supabase_admin in the public schema"). Migrations run as `postgres`, so this is not a gap for our objects. Record it in the schema doc.
- `storage` schema defaults are left alone; M7 reviews them with the portrait bucket.
- Revoking a privilege that is not present is a no-op, so the migration is safe on stacks or hosted projects that already default to opt-in.
- Do **not** set `auto_expose_new_tables` in `config.toml` (decision D7). The key is deprecated and scheduled for removal; the migration is the durable fix.
- Every later migration must still revoke and grant explicitly. Defense in depth, and it keeps each migration self-describing.

### 4.3 Migration 2 — `20261113110000_enforce_campaign_ownership_integrity.sql`

Purpose: A1 (block deletion of owner accounts) and a database-enforced ownership invariant.

```sql
begin;

-- Fail closed on existing inconsistency instead of repairing it silently.
do $$
begin
  if exists (
    select 1 from public.campaigns as c
    where (select count(*) from public.campaign_members as m
           where m.campaign_id = c.id and m.role = 'owner') <> 1
       or not exists (select 1 from public.campaign_members as m
                      where m.campaign_id = c.id and m.role = 'owner'
                        and m.profile_id = c.owner_id)
  ) then
    raise exception 'campaign ownership is inconsistent; resolve it before applying this migration';
  end if;
end;
$$;

-- A1: an owner's profile (and so their Auth user) cannot be deleted while they own campaigns.
alter table public.campaigns
  drop constraint campaigns_owner_id_fkey,
  add constraint campaigns_owner_id_fkey
    foreign key (owner_id) references public.profiles (id) on delete restrict;

-- Invariant, checked at commit for every affected campaign that still exists:
-- exactly one owner row, and it belongs to campaigns.owner_id.
create function private.assert_campaign_ownership_consistent()
returns trigger
language plpgsql
security definer set search_path = ''
as $$
declare
  affected uuid[];
begin
  if tg_table_name = 'campaigns' then
    affected := array[new.id];
  elsif tg_op = 'INSERT' then
    affected := array[new.campaign_id];
  elsif tg_op = 'DELETE' then
    affected := array[old.campaign_id];
  else
    affected := array[old.campaign_id, new.campaign_id];
  end if;

  if exists (
    select 1 from public.campaigns as c
    where c.id = any (affected)
      and ((select count(*) from public.campaign_members as m
            where m.campaign_id = c.id and m.role = 'owner') <> 1
        or not exists (select 1 from public.campaign_members as m
                       where m.campaign_id = c.id and m.role = 'owner'
                         and m.profile_id = c.owner_id))
  ) then
    raise exception using
      errcode = 'integrity_constraint_violation',
      message = 'campaign_ownership_inconsistent';
  end if;
  return null;
end;
$$;

revoke all on function private.assert_campaign_ownership_consistent()
  from public, anon, authenticated, service_role;

create constraint trigger campaigns_ownership_consistent
  after insert or update of owner_id on public.campaigns
  deferrable initially deferred
  for each row execute function private.assert_campaign_ownership_consistent();

create constraint trigger campaign_members_ownership_consistent
  after insert or update or delete on public.campaign_members
  deferrable initially deferred
  for each row execute function private.assert_campaign_ownership_consistent();

commit;
```

Behaviour:

- **Campaign creation**: the AFTER INSERT trigger adds the owner row in the same transaction; the deferred check passes at commit.
- **Campaign deletion**: membership rows cascade; at commit the campaign no longer exists, so it is skipped. Deliberate campaign deletion is unaffected.
- **Member account deletion**: their membership rows cascade; the owner row is untouched; the check passes.
- **Owner account deletion**: `auth.users` delete → `profiles` cascade → `campaigns` FK `RESTRICT` raises `23503` immediately and the whole deletion rolls back. Through the Admin API or Studio this surfaces as a database error. The account can be deleted after each owned campaign is transferred or deleted.
- **Any write path** (RPC bug, service role, manual SQL) that leaves zero owner rows, two owners, or a mismatch fails at commit with `campaign_ownership_inconsistent`.
- `RESTRICT` is chosen over `NO ACTION` so the failure is immediate and cannot be bypassed by deferring constraints.
- Adding the FK validates 9 existing rows that already satisfy it. The lock is held for milliseconds.

## 5. RPC and authorization specifications

### 5.1 Departure hook

```sql
-- Single place for side effects when a player stops being a member.
-- M1: no player-owned data exists yet, so there is nothing to change.
-- M2: set the player's characters in this campaign to in_party = false.
-- M6: mark the player's adventure participations as 'left' and re-evaluate party visibility.
create function private.handle_campaign_member_departure(p_campaign_id uuid, p_profile_id uuid)
returns void
language plpgsql
set search_path = ''
as $$
begin
  return;
end;
$$;

revoke all on function private.handle_campaign_member_departure(uuid, uuid)
  from public, anon, authenticated, service_role;
```

It is SECURITY INVOKER and callable only by `postgres`. It runs only inside the DEFINER RPCs below, so it always executes as `postgres`. Later milestones replace its body with `create or replace function` in their own migration; they do not edit the RPCs. It must never delete player-owned rows (§6).

### 5.2 `public.leave_campaign(p_campaign_id uuid) returns void`

| Step | Rule | Failure |
| --- | --- | --- |
| 1 | `p_campaign_id` not null | `invalid_parameter_value` / `campaign_membership_campaign_required` |
| 2 | Lock the campaign row `for no key update`, **only if the caller has a membership row in it** | not found → `P0001` / `campaign_membership_unavailable` (same response for unknown, inaccessible, and already-left campaigns, so existence is not disclosed) |
| 3 | Caller is not `campaigns.owner_id` | `P0001` / `campaign_leave_owner_must_transfer` |
| 4 | `delete from public.campaign_members where campaign_id = … and profile_id = caller and role = 'member'` | not found → `campaign_membership_unavailable` |
| 5 | `perform private.handle_campaign_member_departure(p_campaign_id, caller)` | — |

```sql
select campaigns.owner_id into campaign_owner_id
from public.campaigns
where campaigns.id = p_campaign_id
  and exists (select 1 from public.campaign_members as m
              where m.campaign_id = campaigns.id and m.profile_id = caller_id)
for no key update of campaigns;
```

### 5.3 `public.remove_campaign_member(p_campaign_id uuid, p_profile_id uuid) returns void`

| Step | Rule | Failure |
| --- | --- | --- |
| 1 | Both arguments not null | `invalid_parameter_value` / `campaign_member_required` |
| 2 | Lock the campaign `for no key update` where `owner_id = caller` | `insufficient_privilege` / `campaign_member_owner_required` (also for unknown campaigns) |
| 3 | `p_profile_id <> caller` | `P0001` / `campaign_member_remove_owner` |
| 4 | Delete the target's row `where role = 'member'` | not found → `P0001` / `campaign_member_unavailable` |
| 5 | `perform private.handle_campaign_member_departure(p_campaign_id, p_profile_id)` | — |

### 5.4 `public.transfer_campaign_ownership(p_campaign_id uuid, p_profile_id uuid) returns void`

| Step | Rule | Failure |
| --- | --- | --- |
| 1 | Both arguments not null | `invalid_parameter_value` / `campaign_transfer_target_required` |
| 2 | Lock the campaign `for no key update` where `owner_id = caller` | `insufficient_privilege` / `campaign_transfer_owner_required` |
| 3 | `p_profile_id <> caller` | `P0001` / `campaign_transfer_self` |
| 4 | Lock the target's membership row `for update`: same campaign, `role = 'member'`, and the Auth user is not soft-deleted (`auth.users.deleted_at is null`) | `P0001` / `campaign_transfer_target_unavailable` |
| 5 | Demote: `update … set role = 'member' where campaign_id = … and profile_id = caller and role = 'owner'` | not found → `integrity_constraint_violation` / `campaign_ownership_inconsistent` (defensive) |
| 6 | Promote: `update … set role = 'owner' where campaign_id = … and profile_id = p_profile_id` | — |
| 7 | `update public.campaigns set owner_id = p_profile_id where id = p_campaign_id` | — |

Demote **before** promote: `campaign_members_one_owner_idx` is a non-deferrable unique index checked per row. All three writes happen in one function call, so they commit or roll back together, and the deferred constraint trigger re-verifies the result at commit. The old owner stays in the campaign as a `member`. `campaigns.updated_at` changes through the existing trigger.

Transfers are immediate and need no acceptance from the target (decision D1). Pending invitations stay pending and are managed by the new owner (decision D2).

### 5.5 Concurrency

Every membership-changing path locks the same `campaigns` row with `FOR NO KEY UPDATE` before touching `campaign_members`: invitation send and respond, leave, remove, transfer, an owner's direct `UPDATE` of name or description (row lock), and campaign deletion (stronger lock). These locks conflict with each other, so operations on one campaign are serialized while other campaigns are unaffected. `FOR NO KEY UPDATE` rather than `FOR UPDATE` avoids blocking unrelated child-row inserts (for example, M2 character inserts that take `FOR KEY SHARE`).

| Race | Outcome |
| --- | --- |
| Two transfers by the owner | The first commits; the second re-reads `owner_id` after waiting and raises `campaign_transfer_owner_required`. |
| Transfer to X while X leaves | Leave first → transfer gets `campaign_transfer_target_unavailable`. Transfer first → X is the owner and gets `campaign_leave_owner_must_transfer`. |
| Remove X while transferring to X | Whichever locks first wins; the other gets `…_unavailable` or `…_owner_required`. |
| Old owner edits details while a transfer commits | The UPDATE waits, re-evaluates the RLS `owner_id = auth.uid()` qualifier on the new row version, and updates 0 rows. The frontend already reports "could not be updated by this account". |
| Invitation accepted while the owner deletes the campaign | Unchanged from today. |

### 5.6 Grants, RLS, and compatibility

```sql
revoke all on function
  public.leave_campaign(uuid),
  public.remove_campaign_member(uuid, uuid),
  public.transfer_campaign_ownership(uuid, uuid)
  from public, anon, authenticated, service_role;
grant execute on function
  public.leave_campaign(uuid),
  public.remove_campaign_member(uuid, uuid),
  public.transfer_campaign_ownership(uuid, uuid)
  to authenticated;
```

No table grants or RLS policies change. Clients still cannot insert, update, or delete `campaign_members`, or update `campaigns.owner_id`. The RPCs are the only membership write path besides invitation acceptance.

Existing policies already produce the correct access after each operation, because they key on membership rows and `campaigns.owner_id`:

| Existing object | After leave/remove | After transfer |
| --- | --- | --- |
| Campaign SELECT policy | Departed player sees nothing | Both players can still read |
| Campaign UPDATE/DELETE policies | n/a | Only the new owner matches |
| Roster SELECT policy, `get_campaign_roster` | Empty for the departed player | Roles swapped |
| `send_`/`list_campaign_outgoing_`/`cancel_campaign_invitation` | n/a | New owner only; sees the previous owner's pending invitations |
| `respond_to_campaign_invitation` | Re-invite and acceptance work (no `already_member` conflict) | Unchanged |
| Auth, username sign-in, Edge Function | Unchanged | Unchanged |

| Action | Anon | Non-member | Member | Owner |

## 6. Data retention and ownership rules

### 6.1 Principles (binding on M2–M8)

1. **Departure is a loss of access, not a deletion.** Leaving or being removed deletes only the membership row. All access to campaign data depends on `campaign_id in (select private.current_campaign_ids())`, so access ends in the same transaction.
2. **Player-owned rows reference the campaign and the player, never the membership.** Future tables use `campaign_id → campaigns(id) on delete cascade` and `owner_id`/`author_id → profiles(id) on delete cascade`. They must **not** reference `campaign_members.id` or `campaign_members (campaign_id, profile_id)`, because that FK would either cascade player data away on departure or block leaving.
3. **The departure hook may only change state** (for example `in_party`, participant status). It never deletes player-owned rows.
4. **Rejoining restores access to retained data** with no migration or copy step, because the data is keyed by `(campaign_id, owner_id)`.
5. **The campaign owner gains no access to departed players' private data**, consistent with A3 and the M03 matrix.

### 6.2 Outcomes by event

| Event | Membership row | Invitation history | Player-owned data (by milestone) |
| --- | --- | --- | --- |
| **Leave** | Deleted | Kept (accepted/declined/cancelled rows remain) | M2: characters kept, `in_party = false`, invisible to everyone (the owner is no longer a member). M3: items and currency kept with the character. M4: private notes kept, invisible. Campaign notes kept, still readable and editable by current members, attribution kept (see open question Q3). M5: nothing changes; adventures are hidden by RLS and personal and side ones return when the player rejoins, and main adventures stay with the members (M03.5 D6). M6 (D9, built): in a shared thread the participation becomes `left` and the adventure stays with the remaining participants; a thread where the player is the only accepted participant is kept, its party share ends, and its pending proposals and invitations are deleted; proposals and invitations to their characters, and their approvals, are deleted. |
| **Removed** | Deleted | Kept | Identical to leaving. No block-list: the owner can re-invite at any time. |
| **Rejoin** (new invitation accepted) | New row: new `id`, new `joined_at`, `role = 'member'` | New accepted row | All retained data becomes visible to its owner again. Characters stay `in_party = false` until the owner re-adds them (so party membership is an explicit choice). M5: the player's own adventures reappear unchanged. M6 (D9, built): participations in shared threads stay `left`; rejoining one needs a new adventure invitation (consent model). Sole threads return unchanged and private. Private notes reappear to their author. |
| **Ownership transfer** | Old owner → `member`, target → `owner` | Pending invitations stay pending; the new owner manages them; recipients still see the original inviter's username | No change. Campaign ownership grants no access to other players' private data. |
| **Member deletes account** | Cascades | Their invitation rows cascade | Their own player-owned data cascades with their profile. Other players' data is untouched. |
| **Owner tries to delete account** | — | — | Blocked (`23503`) until each owned campaign is transferred or deleted. |
| **Owner deletes campaign** | All cascade | All cascade | All campaign data, including other players' characters and notes, cascades. This stays a deliberate, owner-only action with confirmation. **M2 must update the confirmation copy** to say other players' data is deleted. |

### 6.3 Known edge: soft-deleted accounts

GoTrue can soft-delete a user (`deleted_at` set, rows kept). The FK does not fire. A soft-deleted owner keeps owning their campaigns, and a soft-deleted member keeps a membership row. M1 excludes soft-deleted accounts as transfer targets. A fuller treatment needs a decision once an account-deletion flow exists (Q5).

## 8. Migration safety

### 8.1 Pre-flight (read-only, before `db:migrate`)

1. `git status` is clean or contains only M1 work; existing uncommitted work is never overwritten.
2. `npm run supabase:status` shows the stack running; `supabase_migrations.schema_migrations` lists exactly the six existing versions.
3. Record baselines with a read-only transaction: row counts of `profiles`, `campaigns`, `campaign_members`, `campaign_invitations` (by status); the ownership-consistency query from §4.3 (expect 0 rows); `pg_default_acl`; function ACLs.
4. Optional safety net, written outside the repository (for example, the session scratchpad):
   `docker exec supabase_db_backend pg_dump -U postgres --data-only --schema=public --schema=auth -Fc > <scratch>/pre-m1.dump`
5. Run the existing suites for a baseline: `npm test`, `npm run test:e2e`, `npm run test:local-supabase`.

### 8.2 Apply

Write migrations one phase at a time and run `npm run db:migrate` after each. Each file is one transaction; any failure (including the §4.3 precondition) rolls it back with no partial state, and the CLI does not record the version.

### 8.3 Post-migration verification (read-only)

| Check | Expected |
| --- | --- |
| Row counts | Identical to the baseline |
| Ownership consistency query | 0 rows |
| `pg_default_acl` (postgres, public) | No entries for anon/authenticated/service_role on `r`, `S`, `f` |
| `pg_default_acl` (postgres, global, `f`) | `{postgres=X/postgres}` (PUBLIC removed) |
| `pg_get_constraintdef('campaigns_owner_id_fkey')` | `… ON DELETE RESTRICT` |
| `pg_trigger` | Two constraint triggers, deferrable, initially deferred |
| `has_function_privilege` | `authenticated` can execute the three RPCs; `anon`, `service_role`, `public` cannot; nobody but postgres can execute the two private functions |
| Existing function and table ACLs | Unchanged from the baseline |
| After `npm run supabase:stop` + `supabase:start` | Default ACL results unchanged (confirms the CLI does not re-grant on start) |

### 8.4 Rollback

Migrations are forward-only; never edit an applied migration or use `migration repair` to fake a rollback. If a change must be reverted, add a new compensating migration:

| Migration | Compensating SQL | Data impact |
| --- | --- | --- |
| 1 | Re-grant the default privileges (not recommended) | None |
| 2 | Drop both constraint triggers and the function; swap the FK back to `on delete cascade` | None |
| 3 | Drop the three RPCs and the hook | Leaves, removals, and transfers already performed stay in effect. A wrongly removed player is restored by re-inviting; a wrong transfer is undone by the new owner transferring back. |

The `pg_dump` from §8.1 is a last resort for local data only, restored by hand into specific tables. `db:reset` is not a rollback mechanism.

### 8.5 Test-data safety

Integration tests create their own uniquely named accounts and campaigns, delete their campaigns in `finally`, and never touch pre-existing rows. Checks that need destructive SQL (deleting an Auth user, breaking the ownership invariant) run inside `begin; … rollback;` through `localDatabaseQuery`, so nothing persists. Test accounts are left in local Auth as today (audit finding 7). Because of the new FK, any future cleanup that deletes test users must delete or transfer their campaigns first.

## 9. Testing and validation strategy

### 9.1 Integration — `e2e/local-supabase-membership.spec.ts` (new)

Create accounts with the same sign-up approach as the invitation test, and add members through the real invitation RPCs (not direct inserts) so the tests also exercise the full lifecycle.

**Default privileges**
- In a rolled-back transaction as `postgres`: create a scratch table and function in `public` and a function in `private`; assert `has_table_privilege` / `has_function_privilege` are false for `anon`, `authenticated`, `service_role` (and `public` for functions).

**Leave**
- A member leaves: the call succeeds; their `campaigns`, `campaign_members`, and `get_campaign_roster` reads return empty; the owner's roster no longer lists them; the member count drops by one.
- Leaving again → `campaign_membership_unavailable`.
- The owner leaves → `campaign_leave_owner_must_transfer`; the owner row is intact.
- A non-member leaves a real campaign, and anyone leaves a random UUID → the same `campaign_membership_unavailable` (no existence leak).
- Anonymous → error (no EXECUTE); null argument → `22023`.
- **Rejoin**: the owner re-invites the departed player (no `already_member` error); acceptance restores reads; the roster shows `role = 'member'` with a new `joined_at` (checked through `localDatabaseQuery`).

**Remove**
- The owner removes a member: the removed player loses all reads; the roster updates.
- A member tries to remove another member, or the owner → `42501`.
- The owner removes themselves → `campaign_member_remove_owner`.
- The owner removes a non-member or random UUID → `campaign_member_unavailable`.
- An owner of campaign A targets campaign B (owned by someone else) → `42501`.
- A removed player can be re-invited and rejoin.

**Transfer**
- The owner transfers to a member: `campaigns.owner_id` is the target; roles are swapped; exactly one owner row exists.
- The old owner: name update and delete affect 0 rows; `send_campaign_invitation` → `42501`; outgoing list empty; can now leave.
- The new owner: can update details, invite, see and cancel a pending invitation the old owner sent; cannot leave (`…_must_transfer`).
- Self → `campaign_transfer_self`; non-member or random UUID → `campaign_transfer_target_unavailable`; member or anonymous caller → denied; null → `22023`.
- Direct writes stay denied: updating `campaigns.owner_id`, updating `campaign_members.role`, deleting `campaign_members` → `42501`.

**Concurrency** (`Promise.all` from separate clients)
- Two transfers to different members: exactly one succeeds; the other gets `campaign_transfer_owner_required`; the invariant holds.
- Transfer to X while X leaves: exactly one succeeds with the error from §5.5; the invariant holds.
- Remove X while transferring to X: exactly one succeeds; the invariant holds.
- Leave while the owner deletes the campaign: no error other than `campaign_membership_unavailable`; no orphaned rows.

**Integrity** (rolled-back transactions as `postgres`)
- Demoting the owner row without promoting another, then `set constraints all immediate` → `campaign_ownership_inconsistent`.
- Setting `campaigns.owner_id` to a member without changing roles → the same error.
- Deleting the owner's `auth.users` row → `23503`; deleting their campaign first, then the user → succeeds (inside the rolled-back transaction).
- Deleting a member's `auth.users` row → succeeds, cascades only their membership, and the invariant holds.

## 11. Acceptance criteria (M1 as a whole)

1. A member can leave a campaign from the Party panel; access ends immediately and is enforced by RLS.
