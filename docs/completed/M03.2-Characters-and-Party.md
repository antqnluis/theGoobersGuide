## Overview and objectives

M2 lets each player keep campaign-scoped characters with a private-by-default sheet, and turns the party from "everyone in the roster" into "members who own an active, in-party character" (approved decision A2).

M2 delivers:

1. **`characters` and `character_sheets` tables** with RLS, explicit grants, and declarative integrity: one active character per player per campaign (partial unique index), party participation only for active characters (check constraint), and immutable campaign and owner (trigger).
2. **Three RPCs** for state transitions that must be atomic and serialized with membership changes: `create_character`, `set_character_status`, `set_character_in_party`.
3. **The departure hook** (`private.handle_campaign_member_departure`) filled in: leaving or removal clears `in_party` and never deletes characters.
4. **A "My characters" destination** at the camp's tent (the dormant `empty-tent` prop becomes a place), with create, edit, sheet, status, party, sharing, and delete flows.
5. **The Party panel** shows each member's in-party character and opens shared sheets read-only.
6. **Updated copy** for campaign deletion, leaving, and removal now that characters are affected.
7. **Tests**: multi-account integration tests against the local stack (including attempts to bypass the frontend), unit tests, and mocked and real-stack browser tests.

## Approved decisions

### From the M03 review and the M2 brief (finalized)

| # | Decision | M2 consequence |
| --- | --- | --- |
| A2 | Party = campaign members who own an active, in-party character. | Party is derived from `characters` + `campaign_members`; no party table. |
| A3 | Sheets are private by default with owner-controlled sharing. | `sheet_visibility` default `'private'`; summary and sheet are separate tables because RLS is per row. |
| B1 | Characters exist only inside campaigns; each belongs to exactly one campaign and one owning player. | `campaign_id` and `owner_id` are `not null` FKs; there is no campaign-less path. |
| B2 | No transfer between campaigns or players. | No update grant on `campaign_id`/`owner_id`, plus a trigger that rejects changes from every write path. |
| B3 | Several characters per player per campaign, at most one `active`. | Partial unique index `(campaign_id, owner_id) where status = 'active'`. |
| B4 | Only an active character may be in the party. | `check (not in_party or status = 'active')`. |
| B5 | Retired and deceased characters are kept as history. | Status change never deletes; summaries stay readable to members. |
| B6 | A replacement may be created once the previous active character is retired or deceased. | The unique index frees the slot as soon as the status leaves `active`. |
| B7 | Leaving or removal keeps the character, revokes access, and removes it from the party. | Departure hook sets `in_party = false`; RLS requires current membership. |
| B8 | Rejoining restores access without returning characters to the party. | No hook on rejoin; `in_party` stays `false` until the owner re-adds it. |
| B9 | Deleting a campaign deletes its characters, with appropriate confirmation. | `on delete cascade`; the deletion confirmation names characters and sheets. |
| B10 | Campaign ownership grants no access to another player's private sheet. | No policy mentions `campaigns.owner_id`. |
| B11 | Keep the direct `characters.campaign_id` and `characters.owner_id` relationships. | Both reference `campaigns(id)` / `profiles(id)`, never `campaign_members` (M03.1 §6.1 rule 2). |

### Decided during M2 planning (2026-11-13)

| # | Question | Decision |
| --- | --- | --- |
| C1 | Does a new active character join the party automatically? | **Opt-in, pre-ticked.** Database default `in_party = false`; `create_character` takes `p_in_party`; the create form's "Join the party" checkbox is ticked by default. Joining is always an explicit owner choice, as after rejoining. |
| C2 | Who can read a shared sheet? | **All current campaign members.** `sheet_visibility in ('private', 'campaign')`. The value is named `campaign`, not the roadmap's `party`, because "party" now means A2. |

## 2. Database schema, constraints, and relationships

### 2.1 `public.characters` (summary, readable by current members)

```sql
create table public.characters (
  id uuid primary key default gen_random_uuid(),
  campaign_id uuid not null references public.campaigns (id) on delete cascade,
  owner_id uuid not null default auth.uid() references public.profiles (id) on delete cascade,
  name text not null,
  species text,
  class_name text,
  subclass text,
  background text,
  level integer not null default 1,
  status text not null default 'active',
  in_party boolean not null default false,
  sheet_visibility text not null default 'private',
  status_changed_at timestamptz not null default now(),
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),

  constraint characters_name_check check (
    name = btrim(name) and char_length(name) between 1 and 80 and name !~ '[[:cntrl:]]'
  ),
  constraint characters_details_check check (
    (species is null or (species = btrim(species) and char_length(species) between 1 and 60 and species !~ '[[:cntrl:]]'))
    and (class_name is null or (class_name = btrim(class_name) and char_length(class_name) between 1 and 60 and class_name !~ '[[:cntrl:]]'))
    and (subclass is null or (subclass = btrim(subclass) and char_length(subclass) between 1 and 60 and subclass !~ '[[:cntrl:]]'))
    and (background is null or (background = btrim(background) and char_length(background) between 1 and 60 and background !~ '[[:cntrl:]]'))
  ),
  constraint characters_level_check check (level between 1 and 20),
  constraint characters_status_check check (status in ('active', 'retired', 'deceased')),
  constraint characters_sheet_visibility_check check (sheet_visibility in ('private', 'campaign')),
  constraint characters_party_requires_active check (not in_party or status = 'active'),

  -- Targets for later composite FKs (M5 participants: same campaign, same owner).
  constraint characters_id_campaign_key unique (id, campaign_id),
  constraint characters_id_owner_key unique (id, owner_id)
);

-- B3: at most one active character per player per campaign, for every write path.
create unique index characters_one_active_per_player_idx
  on public.characters (campaign_id, owner_id) where status = 'active';

-- Listing by campaign, the campaign FK cascade, and the departure hook's update.
create index characters_campaign_owner_idx on public.characters (campaign_id, owner_id);
-- The profiles FK cascade.
create index characters_owner_id_idx on public.characters (owner_id);
```

Notes:

- Text rules match `profiles_display_name_check` (trimmed, bounded, no control characters). Empty optional fields are stored as `null`; the RPC and the frontend normalize `''` to `null`.
- `status_changed_at` gives history an order ("Retired 12 Mar") and is set by the guard trigger whenever `status` changes, whatever the write path.
- No `portrait_path` (M7) and no currency columns (M3). Each later milestone adds its own columns or tables.
- The partial unique index is the concurrency guarantee: two transactions inserting or reactivating an active character for the same player serialize on the index entry, and the second fails with `23505` once the first commits. No advisory lock or application check is needed.

### 2.2 `public.character_sheets` (1:1 body, owner always, members when shared)

```sql
create table public.character_sheets (
  character_id uuid primary key references public.characters (id) on delete cascade,
  max_hp integer,
  current_hp integer,
  temp_hp integer not null default 0,
  armor_class integer,
  speed integer,
  sheet jsonb not null default '{"version": 1}'::jsonb,
  updated_at timestamptz not null default now(),

  constraint character_sheets_hp_check check (
    (max_hp is null or max_hp between 1 and 9999)
    and (current_hp is null or current_hp between 0 and 9999)
    and (max_hp is null or current_hp is null or current_hp <= max_hp)
    and temp_hp between 0 and 9999
  ),
  constraint character_sheets_armor_class_check check (armor_class is null or armor_class between 0 and 99),
  constraint character_sheets_speed_check check (speed is null or speed between 0 and 999),
  constraint character_sheets_sheet_check check (
    octet_length(sheet::text) <= 65536 and private.character_sheet_is_valid(sheet)
  )
);
```

- Hit points, temporary hit points, armor class, and speed are columns because they change mid-session and are patched individually; the body is `jsonb`, edited as a unit with optimistic concurrency (§5.4).
- The sheet row is created by `create_character` in the same transaction; clients cannot insert or delete sheet rows. It is deleted only by cascade.
- `private.character_sheet_is_valid(jsonb)` is an `immutable` SQL function (structural rules in §5.2). It reads no tables, so it is valid in a check constraint. EXECUTE is revoked from everyone; check constraints do not need it.

### 2.3 Guard trigger (every write path)

```sql
create function private.guard_character_write()
returns trigger
language plpgsql
security definer set search_path = ''
as $$
declare
  needs_membership boolean;
begin
  if tg_op = 'UPDATE' then
    if new.id <> old.id or new.campaign_id <> old.campaign_id or new.owner_id <> old.owner_id then
      raise integrity_constraint_violation using message = 'character_reassignment_forbidden';
    end if;
    if new.status <> old.status then
      new.status_changed_at := now();
    end if;
  end if;

  -- A character can be created, or join the party, only while its owner is a member.
  if tg_op = 'INSERT' then
    needs_membership := true;
  else
    needs_membership := new.in_party and not old.in_party;
  end if;
  if needs_membership and not exists (
    select 1 from public.campaign_members as m
    where m.campaign_id = new.campaign_id and m.profile_id = new.owner_id
  ) then
    raise integrity_constraint_violation using message = 'character_owner_not_member';
  end if;

  return new;
end;
$$;

revoke all on function private.guard_character_write() from public, anon, authenticated, service_role;

create trigger characters_guard_write
  before insert or update on public.characters
  for each row execute function private.guard_character_write();

create trigger characters_set_updated_at
  before update on public.characters
  for each row execute function private.set_updated_at();
create trigger character_sheets_set_updated_at
  before update on public.character_sheets
  for each row execute function private.set_updated_at();
```

The guard is SECURITY DEFINER so its membership lookup is not filtered by the caller's RLS. It applies to `postgres` and `service_role` writes too, so seed scripts and Studio edits cannot break B1, B2, or B7 either. The departure hook's `in_party = false` update passes it. (`private.set_updated_at` and the guard both fire `before update`; PostgreSQL runs them alphabetically, `characters_guard_write` first, which does not matter because they touch different columns.)

### 2.4 Relationships and delete behaviour

| Event | Effect |
| --- | --- |
| Campaign deleted (owner, with confirmation) | `characters` cascade, then `character_sheets` cascade. |
| Member's account hard-deleted | Their `profiles` row cascades their characters and sheets in every campaign. Other players' data is untouched. |
| Owner's account deletion | Still blocked by `campaigns_owner_id_fkey on delete restrict` (unchanged). |
| Character deleted by its owner | Sheet cascades. Frees the active slot if it was active. |
| Leave / remove | Characters kept; `in_party = false` (hook). |
| Ownership transfer | No effect on characters. |

```text
profiles 1─┬─< campaign_members >─┬─1 campaigns
           │                       │
           └──────< characters >───┘        (owner_id, campaign_id: direct FKs, cascade)
                       │ 1
                       └── 1 character_sheets (cascade)
```

## 3. RLS policies and authorization matrix

### 3.1 Grants

```sql
alter table public.characters enable row level security;
alter table public.character_sheets enable row level security;

revoke all on table public.characters, public.character_sheets
  from public, anon, authenticated, service_role;

grant select, delete on table public.characters to authenticated;
grant update (name, species, class_name, subclass, background, level, sheet_visibility)
  on table public.characters to authenticated;

grant select on table public.character_sheets to authenticated;
grant update (max_hp, current_hp, temp_hp, armor_class, speed, sheet)
  on table public.character_sheets to authenticated;
```

No `insert` grant on either table: creation goes through `create_character`. No update grant on `id`, `campaign_id`, `owner_id`, `status`, `in_party`, `status_changed_at`, `created_at`, `updated_at`, or `character_id`: status and party go through RPCs; the rest are immutable or trigger-managed. `service_role` gets nothing (matching the existing tables); server-side tooling uses `postgres`.

### 3.2 Policies

```sql
-- Summaries: current members see the characters of current members, all statuses.
create policy "Members read current members' characters"
on public.characters for select to authenticated
using (
  campaign_id in (select private.current_campaign_ids())
  and exists (
    select 1 from public.campaign_members as m
    where m.campaign_id = characters.campaign_id and m.profile_id = characters.owner_id
  )
);

create policy "Owners update their characters"
on public.characters for update to authenticated
using (owner_id = (select auth.uid()) and campaign_id in (select private.current_campaign_ids()))
with check (owner_id = (select auth.uid()) and campaign_id in (select private.current_campaign_ids()));

create policy "Owners delete their characters"
on public.characters for delete to authenticated
using (owner_id = (select auth.uid()) and campaign_id in (select private.current_campaign_ids()));

-- Sheets: the owner always; other current members only when shared.
create policy "Owners and shared members read sheets"
on public.character_sheets for select to authenticated
using (
  exists (
    select 1 from public.characters as c   -- filtered by the characters SELECT policy
    where c.id = character_sheets.character_id
      and (c.owner_id = (select auth.uid()) or c.sheet_visibility = 'campaign')
  )
);

create policy "Owners update their sheets"
on public.character_sheets for update to authenticated
using (
  exists (
    select 1 from public.characters as c
    where c.id = character_sheets.character_id
      and c.owner_id = (select auth.uid())
      and c.campaign_id in (select private.current_campaign_ids())
  )
)
with check (
  exists (
    select 1 from public.characters as c
    where c.id = character_sheets.character_id
      and c.owner_id = (select auth.uid())
      and c.campaign_id in (select private.current_campaign_ids())
  )
);
```

Why the summary policy checks the character owner's membership with a plain `exists` on `campaign_members` (under the caller's RLS) rather than a new SECURITY DEFINER helper: a helper such as `is_member(campaign, profile)` executable by `authenticated` would let any account probe arbitrary memberships. The caller can already read the roster of their own campaigns, so the `exists` discloses nothing new. The second condition hides a departed player's characters from everyone (M03.1 §6.2) and restores them on rejoin.

No policy refers to `campaigns.owner_id`: the campaign owner is an ordinary member for character data (B10).

### 3.3 Authorization matrix

Key: **R** read, **U** update, **D** delete, **—** denied (no rows or `42501`). "Member" = a current member who neither owns the campaign nor the character. "Departed owner" = the character's owner after leaving or removal.

| Action | Anon | Non-member | Member | Campaign owner | Character owner | Departed owner |
| --- | --- | --- | --- | --- | --- | --- |
| Read summaries (all statuses) | — | — | R | R | R | — |
| Create a character in the campaign (`create_character`) | — | `character_campaign_unavailable` | own only | own only | own only | `character_campaign_unavailable` |
| Edit name/species/class/subclass/background/level | — | — | — (0 rows) | — (0 rows) | U | — |
| Change status (`set_character_status`) | — | `character_unavailable` | `character_unavailable` | `character_unavailable` | yes | `character_unavailable` |
| Join / leave party (`set_character_in_party`) | — | `character_unavailable` | `character_unavailable` | `character_unavailable` | yes (join only when active) | `character_unavailable` |
| Change `sheet_visibility` | — | — | — | — | U | — |
| Read sheet, `private` | — | — | **—** | **—** | R | — |
| Read sheet, `campaign` | — | — | R | R | R | — |
| Edit sheet (HP, AC, speed, body) | — | — | — | — | U | — |
| Delete character | — | — | — (0 rows) | — (0 rows) | D | — |
| Rewrite `campaign_id`, `owner_id`, `id`, `status`, `in_party` directly | — | — | `42501` | `42501` | `42501` (no column grant) | — |

## 4. Character creation, editing, deletion, and visibility workflows

### 4.1 Common RPC prelude

Every M2 RPC:

1. Rejects null required arguments with `22023`.
2. Locks the campaign row **`for share`**, and only where the caller is a current member. Not found → the RPC's "unavailable" error (same for unknown, inaccessible, departed).
3. For per-character RPCs, locks the character row `for update` where `owner_id = caller` and `campaign_id` matches. Not found → `character_unavailable`.

Lock order is always `campaigns` → `characters`, the same order as `leave_campaign`/`remove_campaign_member` → hook, so the two cannot deadlock.

For per-character RPCs, the campaign id is first read without a lock (`select campaign_id from characters where id = p_character_id and owner_id = caller`), then the campaign is locked as above, then the character row is locked and re-read. If the character vanished or changed hands in between (it cannot change hands, but it can be deleted), the RPC returns `character_unavailable`.

### 4.2 `public.create_character(...) returns uuid`

```sql
create function public.create_character(
  p_campaign_id uuid,
  p_name text,
  p_species text default null,
  p_class_name text default null,
  p_subclass text default null,
  p_background text default null,
  p_level integer default 1,
  p_in_party boolean default false
) returns uuid
language plpgsql security definer set search_path = ''
```

| Step | Rule | Failure |
| --- | --- | --- |
| 1 | `p_campaign_id` not null | `22023` / `character_campaign_required` |
| 2 | Normalize: `btrim` all text, `''` → `null`; `p_level` null → 1; `p_in_party` null → false | — |
| 3 | Name passes the §2.1 rule | `22023` / `character_name_invalid` |
| 4 | Optional fields pass the rule; level in 1–20 | `22023` / `character_details_invalid` / `character_level_invalid` |
| 5 | Lock the campaign `for share` where the caller is a member | `P0001` / `character_campaign_unavailable` |
| 6 | Insert into `characters` (`owner_id = caller`, `status = 'active'`, `in_party = p_in_party`) | `unique_violation` on `characters_one_active_per_player_idx` → `P0001` / `character_active_exists` |
| 7 | Insert the `character_sheets` row with defaults | — |
| 8 | Return the new id | — |

The unique-violation handler checks `get stacked diagnostics … constraint_name` and re-raises anything else unchanged. Steps 3–4 duplicate the check constraints so the client gets stable error codes; the constraints remain the backstop.

### 4.3 Editing

- **Summary fields**: direct `update` of the granted columns, `.eq('id', characterId).select(fields).maybeSingle()`; `null` result → "This character could not be updated by this account." Allowed in every status (fixing a retired character's details is legitimate history curation).
- **Sheet**: §5.4.
- **Visibility**: direct update of `sheet_visibility` (owner only via RLS). Takes effect on the next read by others; there is no cached copy server-side.

### 4.4 Status: `public.set_character_status(p_character_id uuid, p_status text) returns void`

| Step | Rule | Failure |
| --- | --- | --- |
| 1 | Both arguments not null; `p_status in ('active','retired','deceased')` | `22023` / `character_required` / `character_status_invalid` |
| 2 | Prelude (§4.1) | `P0001` / `character_unavailable` |
| 3 | Same status → return (idempotent) | — |
| 4 | To `retired` or `deceased`: `update … set status = p_status, in_party = false` | — |
| 5 | To `active`: `update … set status = 'active'` (`in_party` stays false, C3) | `unique_violation` → `character_active_exists` |

Allowed transitions (C3): every pair among `active`, `retired`, `deceased`. The one-active rule is the only restriction. `status_changed_at` is set by the guard.

### 4.5 Party: `public.set_character_in_party(p_character_id uuid, p_in_party boolean) returns void`

| Step | Rule | Failure |
| --- | --- | --- |
| 1 | Both arguments not null | `22023` / `character_required` |
| 2 | Prelude (§4.1) | `P0001` / `character_unavailable` |
| 3 | Unchanged value → return | — |
| 4 | Joining requires `status = 'active'` | `P0001` / `character_not_active` |
| 5 | `update … set in_party = p_in_party` | — |

Because only one character per player can be active and only active characters can be in the party, **a player has at most one in-party character per campaign** without a separate constraint.

### 4.6 Concurrency

`for share` on `campaigns` conflicts with `for no key update` (leave, remove, transfer, invitation responses, owner edits) and with campaign deletion, but not with other `for share` locks. Character RPCs from different players therefore run in parallel, while membership changes wait for them and vice versa.

| Race | Outcome |
| --- | --- |
| Two `create_character` calls by one player (double click, two devices) | Both lock `for share`; the second insert waits on the unique index and fails with `character_active_exists` when the first commits. Exactly one active character. |
| `create_character` and `set_character_status(old, 'active')` by one player | Same index; whichever commits first wins, the other gets `character_active_exists`. |
| `set_character_in_party(true)` while the owner is removed | Remove first → the RPC finds no membership → `character_unavailable`. RPC first → remove waits, then the hook clears `in_party`. Either way the character ends out of the party. |
| `create_character` while the player leaves | Leave first → `character_campaign_unavailable`. Create first → the character exists with the requested `in_party`; the hook then clears it. |
| Status change while the campaign is deleted | The deletion's lock blocks the RPC; afterwards the row is gone → `character_unavailable`. |
| Retire on device A while device B edits the name | Independent columns; both apply (row lock serializes them). |
| Direct writes (service role, SQL) that bypass the RPCs | The unique index, the party check, and the guard trigger still hold. A direct `in_party = true` insert or update racing a leave is the one path not serialized by the campaign lock; the guard's membership check makes it fail if the leave committed first, and the hook clears it if the leave commits after. |

Invariants after any interleaving (asserted by tests): no `(campaign_id, owner_id)` with two active rows; no `in_party` row whose status is not active; no `in_party` row whose owner is not a current member.

### 4.7 Deletion

Direct `delete … .eq('id', id).select('id').maybeSingle()` (pattern of `deleteCampaign`); `null` → "This character could not be deleted by this account." Inline confirmation (C4): "Delete **{name}** permanently? Their sheet will be removed and this can't be undone. To keep them as history, retire them instead." Buttons "Yes, delete character" ("Deleting…") and "Keep {name}".

### 4.8 Visibility summary

| Data | Who sees it |
| --- | --- |
| Summary (name, species, class, subclass, background, level, status, in-party, visibility) | Every current member, for characters whose owner is a current member |
| Sheet, `private` | The owner while a member |
| Sheet, `campaign` | Every current member |
| Anything, after leaving or removal | Nobody, including the owner, until they rejoin |

## 5. Character sheet data structure and validation

### 5.1 Body, version 1

```ts
type AbilityKey = 'str' | 'dex' | 'con' | 'int' | 'wis' | 'cha'
type SkillKey =
  | 'acrobatics' | 'animal_handling' | 'arcana' | 'athletics' | 'deception' | 'history'
  | 'insight' | 'intimidation' | 'investigation' | 'medicine' | 'nature' | 'perception'
  | 'performance' | 'persuasion' | 'religion' | 'sleight_of_hand' | 'stealth' | 'survival'

type CharacterSheetBody = {
  version: 1
  abilities: Record<AbilityKey, number>                    // integers 1–30, default 10
  saving_throws: AbilityKey[]                              // proficient saves, unique
  skills: Partial<Record<SkillKey, 'proficient' | 'expertise'>>
  attacks: { name: string; bonus: string; damage: string; notes: string }[]  // ≤ 30 rows
  features: string                                         // ≤ 8,000 chars
  spells: string                                           // ≤ 8,000 chars (structured spells later)
  notes: string                                            // ≤ 8,000 chars, backstory/personality
  alignment: string                                        // ≤ 40 chars
  experience: number | null                                // integer 0–1,000,000
}
```

Derived values (ability modifiers, proficiency bonus from `characters.level`, save and skill bonuses, initiative, passive Perception) are computed in the client and never stored, so they cannot disagree with their inputs. Equipment and currency are M3 and are not part of the body.

### 5.2 Validation layers

| Layer | Rules |
| --- | --- |
| Database (`character_sheets_sheet_check`) | Object; ≤ 64 KiB; top-level keys ⊆ the v1 list; `version` absent or `1`; `abilities` absent or an object whose keys ⊆ the six and whose values are integers 1–30; `saving_throws` absent or an array of ability keys; `skills` absent or an object with keys ⊆ the eighteen and values in (`proficient`, `expertise`); `attacks` absent or an array of ≤ 30 objects. Free-text lengths are bounded by the size cap only. |
| Database (columns) | HP, AC, speed ranges and `current_hp ≤ max_hp` (§2.2). |
| Frontend (`characterValidation.ts`) | Everything above plus the per-field text limits, trimmed text, and the summary rules from §2.1. `normalizeSheet(raw)` turns any stored body (including `{"version":1}` and unknown or missing keys) into a complete v1 object with defaults, so readers never crash on partial data. |

The database enforces the structure other members rely on when a sheet is shared; the client enforces the rest. A future body version adds a migration that widens the check and a client upgrade path in `normalizeSheet`.

### 5.3 Defaults on creation

`character_sheets` row: all HP/AC/speed `null`, `temp_hp = 0`, `sheet = {"version": 1}`. The sheet view shows "Not set" for null vitals and the normalized defaults for the body.

### 5.4 Saving and concurrency

- **Vitals** (HP, temp HP, AC, speed): patch only the changed columns with `.update({...}).eq('character_id', id).select().maybeSingle()`. Last write wins; acceptable because only the owner writes and HP changes are small, frequent, and self-correcting at the table.
- **Body**: save the whole object with `.eq('updated_at', previousUpdatedAt)`. Zero rows → "This sheet changed on another device. Reload it to see the latest version." The cache is updated from the returned row so a vitals change in the same tab does not cause a false conflict.
- No RPC is needed for sheet writes: they touch one row, require no membership serialization, and are fully covered by RLS and the checks.

## 6. Party roster integration and `in_party` behaviour

### 6.1 Definitions

- **Roster**: campaign members (`get_campaign_party`), unchanged.
- **Party** (A2): current members who own a character with `status = 'active' and in_party`. Derived in the client from the roster and the characters query; the database guarantees at most one such character per member. A server-side `private.current_party_campaign_ids()` helper is deferred to M6, which is the first feature whose access depends on party membership.

### 6.2 Data flow

One query per campaign: `from('characters').select(summaryFields).eq('campaign_id', id).order('created_at')`, key `['campaigns', 'characters', campaignId, userId]`. RLS returns exactly the summaries the caller may see. Both the tent ("mine" = `owner_id === userId`) and the Party panel (others' in-party characters) read it.

### 6.3 Party panel

- Each member row keeps its existing name, handle, role, and remove control, and adds one line: the in-party character's name, "Level {n} {species} {class}" (omitting unset parts), or "No character in the party".
- If that character's sheet is shared (`sheet_visibility = 'campaign'`) or it is the viewer's own, a `campaign-text-button` "View sheet" (`aria-label="View {character}'s sheet"`) swaps the panel content for a read-only `CharacterSheet` with "Back to party". Private sheets of others show no button and no placeholder.
- A short count above the list: "{n} of {m} members have a character in the party."
- Retired, deceased, and out-of-party characters do not appear in the Party panel; history lives in the owner's tent.

### 6.4 Camp scene

Sprites stay seated per **account** from the roster (M03 §3: swapping to characters is optional and presentational). Name plates keep showing usernames. Changing seating to party-only is deferred to keep M2 free of scene changes beyond the tent.

### 6.5 `in_party` state machine

```text
                 create (p_in_party)
                        │
   ┌─────── active, in_party ◄──join── active, not in party ◄── reactivate ── retired / deceased
   │             │  leave party ──────────►    ▲      │ retire / die ─────────────►    ▲
   │             │ retire / die (clears in_party) ─────────────────────────────────────┘
   │             │ owner leaves or is removed (hook clears in_party)
   └─────────────┴──► stays active, not in party; invisible until rejoin
```

## 7. Membership departure and rejoining

### 7.1 Departure hook (M2 body)

```sql
create or replace function private.handle_campaign_member_departure(p_campaign_id uuid, p_profile_id uuid)
returns void
language plpgsql
set search_path = ''
as $$
begin
  -- M2: the departed player's characters leave the party. They are kept, never deleted.
  update public.characters
  set in_party = false
  where campaign_id = p_campaign_id and owner_id = p_profile_id and in_party;
  -- M6: mark adventure participations as 'left' and re-evaluate party visibility.
end;
$$;

revoke all on function private.handle_campaign_member_departure(uuid, uuid)
  from public, anon, authenticated, service_role;
```

`create or replace` keeps the existing ACL; the revoke is repeated so the migration is self-describing. The RPCs that call it are unchanged.

### 7.2 Outcomes

| Event | Characters | Sheets | Access |
| --- | --- | --- | --- |
| Leave / removed | Kept; `in_party = false`; status unchanged (an active character stays active) | Kept, visibility unchanged | The departed player sees nothing. Remaining members no longer see the departed player's characters or sheets. |
| Rejoin (new invitation accepted) | Same rows; `in_party` still false | Same rows | Everything reappears to the owner and, per visibility, to members. The owner re-joins the party explicitly. Their active character is still active, so creating another is refused until it is retired, marked deceased, or deleted; the expected path is to re-join the party with it. |
| Ownership transfer | No change | No change | The new owner gains nothing over other players' characters. |
| Campaign deleted | Cascade-deleted | Cascade-deleted | — |
| Member deletes account | Their characters in every campaign cascade | Cascade | — |

### 7.3 Frontend copy changes

- **Leave confirmation**: "Leave **{campaign}**? You'll lose access until the owner invites you again. Your characters are kept and leave the party."
- **Remove confirmation**: "Remove **{name}** from **{campaign}**? They'll lose access until you invite them again. Their characters are kept and leave the party."
- **Delete campaign confirmation** (B9): "Delete **{campaign}** permanently? Its details, member list, and every player's characters and character sheets will be removed. This can't be undone." The button stays "Yes, delete campaign". No count is shown, because the owner cannot see departed players' characters and a partial count would mislead.

## 9. Non-destructive migration strategy

### 9.1 Files (timestamps after `20261113130000`; use the real creation time)

| # | File | Contents |
| --- | --- | --- |
| 1 | `20261114100000_add_characters.sql` | `private.character_sheet_is_valid`, both tables, constraints, indexes, guard and `updated_at` triggers, RLS, revokes, grants, policies. |
| 2 | `20261114110000_add_character_lifecycle.sql` | `create_character`, `set_character_status`, `set_character_in_party` (revoke all, grant EXECUTE to `authenticated`), and the departure hook body. |

Each is wrapped in `begin; … commit;`. The only change to an existing object is the hook's body (`create or replace`, same signature, same ACL). No existing table, policy, grant, or RPC changes. No backfill: no characters exist.

### 9.2 Pre-flight (read-only)

1. `git status` clean or M2-only.
2. `npm run supabase:status`; `schema_migrations` lists exactly the ten versions in §1.5.
3. Baseline in a read-only transaction: row counts of `profiles`, `campaigns`, `campaign_members`, `campaign_invitations` (by status); the M1 ownership-consistency query (0 rows); function and table ACLs.
4. Optional local safety net outside the repo: `docker exec supabase_db_backend pg_dump -U postgres --data-only --schema=public --schema=auth -Fc > <scratchpad>/pre-m2.dump`.
5. Baseline suites: `npm test`, `npm run test:e2e`, `npm run test:local-supabase`.

### 9.3 Apply

One migration per phase with `npm run db:migrate` (from `implementation/backend`). A failure rolls the file back and the CLI does not record it. Then `npm run db:types` and `npx prettier --write src/types/database.ts` (from `implementation/frontend`). Never `db:reset`.

### 9.4 Post-migration checks (read-only)

| Check | Expected |
| --- | --- |
| Existing row counts | Identical to baseline |
| Ownership consistency | 0 rows |
| `relrowsecurity` on both tables | true |
| `has_table_privilege` / `has_column_privilege` | `authenticated`: select, delete, and the listed update columns on `characters`; select and the listed update columns on `character_sheets`; no insert. `anon`, `service_role`, `public`: none. |
| `has_function_privilege` | The three RPCs: `authenticated` only. `private.character_sheet_is_valid`, `private.guard_character_write`, the hook: nobody but `postgres`. |
| `pg_indexes` | `characters_one_active_per_player_idx` is unique and partial (`WHERE status = 'active'`). |
| Existing function/table ACLs | Unchanged |

### 9.5 Rollback (compensating migrations only)

| Migration | Compensation | Data impact |
| --- | --- | --- |
| 2 | Drop the three RPCs; restore the hook's no-op body. | Characters remain; status/party changes stop until re-added. |
| 1 | Drop both tables and the two private functions. | **Deletes all characters and sheets.** Only acceptable before real use; otherwise export first. |

### 9.6 Test-data safety

Integration tests create their own accounts and campaigns and delete their campaigns in `finally` (characters cascade). Destructive SQL (direct inserts as `postgres`, account deletion, invariant violations) runs inside `begin; … rollback;` through `localDatabaseQuery`. Pre-existing rows are never touched.

### 10.1 Integration — `e2e/local-supabase-characters.spec.ts` (new)

Setup: move `createAccount`, `newPlayers`, `invite`, `createCampaign`, `rpcError`, `rpcOk`, and `cleanup` unchanged from `local-supabase-membership.spec.ts` into `e2e/support/localPlayers.ts` and import them from both specs. **Catalog and privileges** (rolled back / read-only): RLS enabled; grants exactly as §9.4; RPC and private function EXECUTE as §9.4; the partial unique index exists.

**Creation**
- A member creates a character: one summary row and one sheet row; `status = 'active'`; `in_party` equals the argument; `owner_id` is the caller.
- A second create while one is active → `character_active_exists`; after retiring the first, a replacement succeeds (B6).
- Non-member, departed player, random UUID → `character_campaign_unavailable` (identical).
- Invalid name, details, and level → their codes; null campaign → `22023`; anonymous → denied.

**Bypass attempts through the API** (publishable key, signed-in member)
- `insert` into `characters` or `character_sheets` → `42501`.
- `update` of `status`, `in_party`, `campaign_id`, `owner_id`, `status_changed_at` → `42501`.
- Another member's or the campaign owner's `update`/`delete` of a character → 0 rows; row unchanged (checked with `localDatabaseQuery`).
- Updating another player's sheet → 0 rows.
- A sheet body that is not an object, too large, has an unknown key, an ability of 31 or 0, or a bad skill value → `23514`; `current_hp > max_hp` → `23514`.

**Bypass attempts in the database** (as `postgres`, rolled back)
- Inserting a second active character for the same player → `23505`.
- Setting `in_party = true` on a retired character → `23514`.
- Changing `campaign_id` or `owner_id` → `character_reassignment_forbidden`.
- Inserting a character for a non-member, or setting `in_party = true` for a departed owner → `character_owner_not_member`.

**Status and party**
- Retire / mark deceased clears `in_party` and sets `status_changed_at`; deceased → active and retired → active succeed when no other is active and leave `in_party = false`; reactivation with another active → `character_active_exists`; same-status calls are no-ops.
- Joining with a non-active character → `character_not_active`; leaving the party always works.
- Another member or the campaign owner calling either RPC on someone else's character → `character_unavailable`.

**Visibility**
- A private sheet is invisible to another member and **to the campaign owner** (empty result), visible to its owner.
- After `sheet_visibility = 'campaign'`, every current member can read it but not update it; switching back hides it again.
- Summaries (all statuses) are readable by every current member; a non-member reads nothing.

**Departure and rejoin**
- A member with an in-party character leaves: the row still exists with `in_party = false` and the same status (via `localDatabaseQuery`); the leaver reads no summaries or sheets; remaining members (including the campaign owner) no longer see that player's characters.
- Removal behaves identically.
- Rejoin through a new invitation: the owner sees their characters and sheet again; `in_party` is still false; `create_character` → `character_active_exists`; joining the party succeeds.

**Cascades** (row counts via `localDatabaseQuery`)
- Deleting the campaign removes every character and sheet in it, including a departed player's.
- Deleting a member's Auth user (rolled back) removes only their characters; others' remain.
- Deleting one's own character removes its sheet and frees the active slot.

**Concurrency** (`Promise.all` from separate clients)
- Five parallel `create_character` calls by one player → exactly one success, four `character_active_exists`.
- Parallel create and reactivate → exactly one active.
- `set_character_in_party(true)` racing `remove_campaign_member` → the character ends with `in_party = false`.
- `create_character` racing `leave_campaign` → no in-party character for a non-member.
- After each: the three §4.6 invariants hold (SQL assertions).

**Regression**: `local-supabase.spec.ts` and `local-supabase-membership.spec.ts` pass unchanged.

**UI against the real stack** (same file): a player opens the tent, creates a character, reloads, and it persists; a second player sees it in the Party panel and, after the first shares it, opens the read-only sheet.

## 12. Acceptance criteria (M2 as a whole)

1. A member can create, edit, retire, mark deceased, reactivate, and delete their own characters in the tent; every change persists across a reload.
2. The database refuses a second active character per player per campaign, including under concurrent requests and direct writes.
3. Only active characters can be in the party; retiring or death removes a character from it in the same statement.
4. Characters can never move to another campaign or owner, by any write path.
5. Sheets are private by default; sharing makes them readable by all current members and nobody else; the campaign owner has no override.
6. Leaving or removal keeps characters, clears `in_party`, and revokes all access, including other members' view of them; rejoining restores access without re-joining the party.
7. Deleting a campaign deletes its characters after a confirmation that says so.
8. The Party panel shows each member's in-party character and opens shared sheets read-only.
9. Existing auth, campaigns, invitations, membership lifecycle, display names, and camp behaviour are unchanged, and their tests pass.
10. Migrations ran with `db:migrate` only; existing row counts are unchanged; no `db:reset`. All §10.4 commands pass and are reported.

## 13. Risks, edge cases, and decisions for review

### Risks

| Risk | Mitigation |
| --- | --- |
| A sheet body edited on two devices loses one edit | Optimistic concurrency on `updated_at` (§5.4); vitals are column patches. |
| Nested RLS (sheet policy → characters policy → roster policy) slows reads as data grows | Indexes on `(campaign_id, owner_id)` and the roster; small row counts; revisit with `explain` if a campaign exceeds a few hundred characters. |
| The DB sheet check drifts from the client's v1 type | One source list of keys in `characterValidation.ts` mirrored by the SQL function; integration tests send every key and a disallowed key. |
| The tent is off-frame at the resting camera, so players may not notice it | Always in the Places list; opening pans to it; the Party panel's empty line links to it ("Create a character in the tent"). |
| `for share` on `campaigns` briefly blocks owner edits of name/description during character RPCs | Single-row RPCs that commit in milliseconds. |
| Unbounded historical characters per player | Not a correctness issue; add a cap later if abuse appears. |
| Soft-deleted accounts keep their characters and membership | Same as M1 Q5; out of scope. |
| Leftover integration-test accounts (595 profiles) | Pre-existing; tests delete their campaigns, which cascades their characters. |

### Edge cases covered

- Double-submit of the create form → one character (`character_active_exists` on the second, shown as a no-op if the first succeeded and the list already has it).
- A player rejoins with a still-active character → no duplicate; they re-join the party with it.
- The only active character is deleted → a new one can be created immediately.
- Ownership transfer to a player with private sheets → the new owner still cannot read them.
- A shared sheet is opened by a member at the moment its owner leaves → the next read returns nothing; the panel shows "This sheet is no longer available."
- An email-only former owner without a username → Party panel naming already falls back via `memberName`.

| # | Recommendation | Alternative |
