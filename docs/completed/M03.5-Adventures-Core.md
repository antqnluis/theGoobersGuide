## Overview and objectives

M5 turns the **Map table**, today unlabeled scenery in the camp, into an Adventures board. A player can write down a personal objective or a side mission for one of their characters, which no one else can see, including the campaign owner. The group can keep its main storyline there, which every current member can read and edit. Each adventure has a status, a next step, a checklist of objectives, and a short log of updates.

M5 delivers:

1. **Four tables** with RLS: `adventures`, `adventure_participants` (written only by `create_adventure` in M5), `adventure_objectives`, and `adventure_updates`. Each has explicit grants and guard triggers that keep keys fixed and enforce limits.
2. **One RPC**, `create_adventure`, which inserts the adventure and the creator's character as its participant in one transaction. Every other write is a direct single-row write covered by RLS and the guards, as notes are.
3. **Visibility helpers** `private.visible_adventure_ids()` and `private.editable_adventure_ids()`, which every policy uses, so no list, count, or embed can leak a private adventure.
4. **Optimistic concurrency** for adventure details, using the same conflict flow as notes.
5. **An Adventures destination at the Map table**: grouped list, create form, detail view with status, next step, objectives, and updates, an edit form, and archive and restore for the creator.
6. **Updated copy** for deleting a campaign and deleting a character.
7. **Tests**: multi-account integration tests against the local stack, including attempts to bypass the frontend, plus unit tests and a mocked browser spec.

### 1.2 Conventions inherited from M1–M4 (mandatory)

- `language plpgsql security definer set search_path = ''`, schema-qualified names.
- Error codes: `insufficient_privilege` (`42501`) for authorization, `P0001` with a snake_case message for state, `invalid_parameter_value` (`22023`) for malformed arguments, `integrity_constraint_violation` (`23000`) for integrity, `23514` for checks.
- Every new table and function: `revoke all … from public, anon, authenticated, service_role`, then explicit grants.
- "Unavailable" responses are the same for unknown, inaccessible, and departed cases.
- Guard triggers pass nested updates through (`pg_trigger_depth() > 1`), so FK `set null` actions from account deletion are never blocked. M03.4 Phase 1 found this the hard way.
- Generated types: `npm run db:types` (backend), then `npx prettier --write src/types/database.ts` (frontend).

## 2. Database schema, constraints, and relationships

### 2.1 Tables

```sql
create table public.adventures (
  id uuid primary key default gen_random_uuid(),
  campaign_id uuid not null references public.campaigns (id) on delete cascade,
  created_by uuid not null default auth.uid() references public.profiles (id) on delete cascade,
  type text not null,
  visibility text not null,
  status text not null default 'pending',
  title text not null,
  description text not null default '',
  next_step text not null default '',
  reference text not null default '',
  updated_by uuid references public.profiles (id) on delete set null,
  status_changed_at timestamptz,
  status_changed_by uuid references public.profiles (id) on delete set null,
  archived_at timestamptz,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),

  constraint adventures_type_check check (type in ('main', 'side', 'personal')),
  -- M6 adds 'party' for shared personal and side adventures; main stays 'campaign'.
  constraint adventures_visibility_check check (visibility in ('participants', 'campaign')),
  constraint adventures_visibility_matches_type check ((type = 'main') = (visibility = 'campaign')),
  constraint adventures_status_check check (status in ('pending', 'in_progress', 'on_hold', 'completed')),
  constraint adventures_title_check check (
    title = btrim(title) and char_length(title) between 1 and 120 and title !~ '[[:cntrl:]]'
  ),
  constraint adventures_description_check check (
    char_length(description) <= 4000 and description !~ '[\x01-\x08\x0B\x0C\x0E-\x1F\x7F]'
  ),
  constraint adventures_next_step_check check (
    next_step = btrim(next_step) and char_length(next_step) <= 280 and next_step !~ '[[:cntrl:]]'
  ),
  constraint adventures_reference_check check (
    reference = btrim(reference) and char_length(reference) <= 280 and reference !~ '[[:cntrl:]]'
  ),
  constraint adventures_id_campaign_key unique (id, campaign_id)
);

create index adventures_campaign_updated_idx on public.adventures (campaign_id, updated_at desc);
create index adventures_creator_idx on public.adventures (created_by, campaign_id);

create table public.adventure_participants (
  id uuid primary key default gen_random_uuid(),
  adventure_id uuid not null,
  campaign_id uuid not null,
  character_id uuid not null,
  profile_id uuid not null,
  -- M5 writes only 'accepted'. The other states are M6's.
  status text not null default 'accepted',
  created_at timestamptz not null default now(),

  constraint adventure_participants_status_check
    check (status in ('proposed', 'invited', 'accepted', 'declined', 'left')),
  constraint adventure_participants_adventure_fkey foreign key (adventure_id, campaign_id)
    references public.adventures (id, campaign_id) on delete cascade,
  constraint adventure_participants_character_campaign_fkey foreign key (character_id, campaign_id)
    references public.characters (id, campaign_id) on delete cascade,
  constraint adventure_participants_character_owner_fkey foreign key (character_id, profile_id)
    references public.characters (id, owner_id) on delete cascade,
  constraint adventure_participants_unique unique (adventure_id, character_id)
);

create index adventure_participants_profile_idx on public.adventure_participants (profile_id, status);
create index adventure_participants_character_idx on public.adventure_participants (character_id);

create table public.adventure_objectives (
  id uuid primary key default gen_random_uuid(),
  adventure_id uuid not null references public.adventures (id) on delete cascade,
  title text not null,
  done boolean not null default false,
  created_by uuid default auth.uid() references public.profiles (id) on delete set null,
  completed_by uuid references public.profiles (id) on delete set null,
  completed_at timestamptz,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),

  constraint adventure_objectives_title_check check (
    title = btrim(title) and char_length(title) between 1 and 200 and title !~ '[[:cntrl:]]'
  ),
  constraint adventure_objectives_done_check check (done = (completed_at is not null))
);

create index adventure_objectives_adventure_idx on public.adventure_objectives (adventure_id, created_at);

create table public.adventure_updates (
  id uuid primary key default gen_random_uuid(),
  adventure_id uuid not null references public.adventures (id) on delete cascade,
  author_id uuid not null default auth.uid() references public.profiles (id) on delete cascade,
  body text not null,
  created_at timestamptz not null default now(),

  constraint adventure_updates_body_check check (
    body = btrim(body) and char_length(body) between 1 and 2000
    and body !~ '[\x01-\x08\x0B\x0C\x0E-\x1F\x7F]'
  )
);

create index adventure_updates_adventure_idx on public.adventure_updates (adventure_id, created_at desc);
```

- `adventures (id, campaign_id)` is unique so that participants, and M8's `adventure_handoffs`, can carry a composite FK that pins them to the adventure's campaign.
- The two participant FKs guarantee that a participant's character belongs to the same campaign and that `profile_id` is that character's owner, for every write path.
- Personal and side adventures always have participants; main adventures never do (D1). `create_adventure` enforces both at creation, and the orphan trigger (§2.3) keeps the first true afterwards.

### 2.2 Visibility helpers

```sql
-- Adventures the caller may read: main adventures of their campaigns, and personal or side
-- adventures where they own an accepted participant. Archived adventures only for their creator.
create function private.visible_adventure_ids()
returns setof uuid
language sql stable security definer set search_path = ''
as $$
  select a.id
  from public.adventures as a
  where a.campaign_id in (select private.current_campaign_ids())
    and (a.archived_at is null or a.created_by = (select auth.uid()))
    and (
      a.type = 'main'
      or exists (
        select 1 from public.adventure_participants as p
        where p.adventure_id = a.id
          and p.profile_id = (select auth.uid())
          and p.status = 'accepted'
      )
    );
$$;

-- The same, minus archived adventures: where objectives and updates may be written.
create function private.editable_adventure_ids()
returns setof uuid
language sql stable security definer set search_path = ''
as $$
  select id from private.visible_adventure_ids() as v(id)
  where not exists (select 1 from public.adventures as a where a.id = v.id and a.archived_at is not null);
$$;
```

Both are executable by `authenticated` (policies run as the caller) and nobody else. Being SECURITY DEFINER, they read `adventure_participants` without its own policy, which avoids recursive RLS between the two tables.

### 2.3 Guards and triggers (every write path)

**`private.guard_adventure_write`** (before update on `adventures`):

1. Nested updates (`pg_trigger_depth() > 1`, an FK `set null` action) pass through.
2. `id`, `campaign_id`, `created_by`, `created_at`, and `visibility` never change → `adventure_reassignment_forbidden` (`23000`). M6's sharing RPCs will set visibility through a path this guard allows.
3. A change between `main` and any other type → `adventure_type_change_forbidden` (D2).
4. An archived row: the only allowed change is the creator clearing `archived_at` with every other column unchanged → otherwise `adventure_archived`. A restore by anyone else → `adventure_archive_creator_only` (`42501`).
5. Archiving (`archived_at` from null to a value): creator only, otherwise `adventure_archive_creator_only` (`42501`). The guard sets `archived_at := now()` whatever the client sent.
6. A status change sets `status_changed_at := now()` and `status_changed_by := auth.uid()`.
7. `updated_by := auth.uid()`.

`private.set_updated_at()` runs after the guard on every update.

**`private.guard_adventure_objective_write`** (before insert or update on `adventure_objectives`):

- Update: `id`, `adventure_id`, `created_by`, and `created_at` never change → `adventure_reassignment_forbidden`.
- Insert: an advisory lock keyed by adventure, then the 50 cap → `adventure_objective_limit_reached`.
- `done` changing to true sets `completed_by := auth.uid()` and `completed_at := now()`; to false clears both.

**`private.guard_adventure_update_insert`** (before insert on `adventure_updates`): an advisory lock keyed by adventure, then the 500 cap → `adventure_update_limit_reached`. Updates have no update grant, so no update guard is needed.

**`private.delete_orphaned_adventure`** (after delete on `adventure_participants`, for each row): deletes the adventure if it is not `main` and has no accepted participant left (D5). When the adventure itself is being deleted, it is already gone and the trigger does nothing.

All four functions are executable by nobody but `postgres`.

### 2.4 `create_adventure`

```sql
create function public.create_adventure(
  p_campaign_id uuid,
  p_type text,
  p_title text,
  p_character_id uuid default null,
  p_next_step text default null,
  p_description text default null
) returns uuid
language plpgsql security definer set search_path = ''
```

| Step | Behaviour |
| --- | --- |
| Arguments | Null campaign or type → `22023` (`adventure_campaign_required`, `adventure_type_invalid`). Title, next step, and description are trimmed and checked against D8 → `adventure_title_invalid`, `adventure_details_invalid` (`22023`). |
| Character | Personal and side need one → `adventure_character_required`. Main must not have one → `adventure_main_has_no_participants` (D1). |
| Campaign | Lock `FOR SHARE` where the caller is a member, as `create_character` does → otherwise `adventure_campaign_unavailable`. |
| Character check | Lock the character `FOR SHARE` where `owner_id = caller` and `campaign_id = p_campaign_id` → otherwise `adventure_character_unavailable` (unknown, another player's, and another campaign's look the same). Any status (D3). |
| Cap | Advisory lock keyed by campaign and creator, then 200 → `adventure_limit_reached`. |
| Insert | The adventure with `visibility` derived from `type`, `updated_by = caller`, then, for personal and side, one `accepted` participant. Returns the id. |

Executable by `authenticated` only. Clients have no insert grant on `adventures` or `adventure_participants`, so this is the only way to create either.

### 2.5 Relationships and delete behaviour

```text
campaigns 1 ──< adventures >── 1 profiles (creator)
                   │  │  │
                   │  │  └──< adventure_updates >── 1 profiles (author)
                   │  └──< adventure_objectives
                   └──< adventure_participants >── 1 characters (same campaign, same owner)
```

| Event | Effect |
| --- | --- |
| Campaign deleted | Every adventure in it cascades, with participants, objectives, and updates. |
| Creator's account deleted | Their adventures cascade, main ones included (D7). Their updates elsewhere cascade. Other attributions become null. |
| Participating character deleted | Its participant rows cascade. A personal or side adventure left with no accepted participant is deleted (D5). |
| Character retired or marked deceased | No effect. |
| Leave or removal | Nothing is changed. Reads and writes stop through RLS (D6). |
| Rejoin | The player's own adventures are readable and editable again. Main adventures are visible again as for any member. |
| Ownership transfer | No effect. The new owner gains nothing. |

## 3. RLS policies and authorization matrix

### 3.1 Grants

```sql
-- RLS enabled and `revoke all … from public, anon, authenticated, service_role` on all four tables.
grant select on table public.adventures to authenticated;
grant update (type, status, title, description, next_step, reference, archived_at)
  on table public.adventures to authenticated;

grant select on table public.adventure_participants to authenticated;

grant select, delete on table public.adventure_objectives to authenticated;
grant insert (adventure_id, title) on table public.adventure_objectives to authenticated;
grant update (title, done) on table public.adventure_objectives to authenticated;

grant select, delete on table public.adventure_updates to authenticated;
grant insert (adventure_id, body) on table public.adventure_updates to authenticated;
```

No client inserts adventures or participants (RPC only), deletes an adventure (archive instead), or writes a participant row.

### 3.2 Policies

```sql
create policy "Readers see visible adventures" on public.adventures
  for select to authenticated using (id in (select private.visible_adventure_ids()));

-- The guard decides what an update may change (archived rows, archive, type).
create policy "Readers edit visible adventures" on public.adventures
  for update to authenticated
  using (id in (select private.visible_adventure_ids()))
  with check (id in (select private.visible_adventure_ids()));

create policy "Readers see participants" on public.adventure_participants
  for select to authenticated using (adventure_id in (select private.visible_adventure_ids()));

create policy "Readers see objectives" on public.adventure_objectives
  for select to authenticated using (adventure_id in (select private.visible_adventure_ids()));
create policy "Editors add objectives" on public.adventure_objectives
  for insert to authenticated with check (adventure_id in (select private.editable_adventure_ids()));
create policy "Editors change objectives" on public.adventure_objectives
  for update to authenticated
  using (adventure_id in (select private.editable_adventure_ids()))
  with check (adventure_id in (select private.editable_adventure_ids()));
create policy "Editors delete objectives" on public.adventure_objectives
  for delete to authenticated using (adventure_id in (select private.editable_adventure_ids()));

create policy "Readers see updates" on public.adventure_updates
  for select to authenticated using (adventure_id in (select private.visible_adventure_ids()));
create policy "Editors post updates as themselves" on public.adventure_updates
  for insert to authenticated
  with check (author_id = (select auth.uid()) and adventure_id in (select private.editable_adventure_ids()));
create policy "Authors delete their updates" on public.adventure_updates
  for delete to authenticated
  using (author_id = (select auth.uid()) and adventure_id in (select private.editable_adventure_ids()));
```

### 3.3 Authorization matrix

Key: **R** read, **C** create, **U** update, **D** delete, **—** denied (no rows, or `42501`). "Member" means a current member with no other role on the adventure. "Participant" means the owner of the accepted participant's character.

| Action | Anon | Non-member | Member | Campaign owner (not participant) | Participant / creator | Departed player |
| --- | --- | --- | --- | --- | --- | --- |
| Create main | — | — | C | C | C | — |
| Create personal or side | — | — | C, own character only | C, own character only | C | — |
| Read main (with objectives, updates) | — | — | R | R | R | — |
| Edit main, its objectives and updates | — | — | U | U | U | — |
| Read personal or side | — | — | **—** | **—** | R | — |
| Edit personal or side | — | — | **—** (0 rows) | **—** (0 rows) | U | — |
| Change type between personal and side | — | — | main: n/a | main: n/a | yes | — |
| Change type to or from main | — | — | `adventure_type_change_forbidden` | same | same | — |
| Archive or restore | — | — | main: `42501` unless creator | same | creator only | — |
| Read an archived adventure | — | — | — | — | creator only | — |
| Edit an archived adventure | — | — | — | — | `adventure_archived` | — |
| Delete an update | — | — | own only | own only | own only | — |
| Write a participant row, move an adventure, change its creator | — | — | `42501` (no grant), and the guard for every path | same | same | — |

**Explicit negatives to test:** the campaign owner cannot read, count, or edit a member's personal or side adventure, or see it through participant, objective, or update reads or PostgREST embeds. A member cannot create an adventure for another player's character or a character from another campaign, insert participants, insert an update as someone else, set `created_by`, `updated_by`, `status_changed_*`, `completed_by`, or timestamps, move an adventure or objective, turn a personal adventure into a main one, archive someone else's main adventure, edit an archived adventure, or exceed a cap. A departed player loses every read and write and gets their own back on rejoining.

## 4. Workflows and requests

### 4.1 Requests

| Action | Request | Zero rows or error |
| --- | --- | --- |
| List | `select(adventureListFields, adventure_participants(character_id), adventure_objectives(done)).eq('campaign_id', id).order('updated_at', { ascending: false })`. List fields omit `description`. | Error → retry state. |
| Open | `select(adventureFields, adventure_participants(…), adventure_objectives(…), adventure_updates(…)).eq('id', id).maybeSingle()`, children ordered | No row → `adventure_unavailable`. |
| Create | `rpc('create_adventure', …)`, then open the new id. | Error codes → their copy (§4.3). |
| Save details | `update({ title, type, description, next_step, reference }).eq('id', id).eq('updated_at', previous).select(adventureFields).maybeSingle()` | No row → re-read: found → `adventure_conflict` (D11), not found → `adventure_unavailable`. |
| Change status | `update({ status }).eq('id', id).select(adventureFields).maybeSingle()` | No row → `adventure_unavailable`. |
| Archive / restore | `update({ archived_at: now or null }).eq('id', id).select(…).maybeSingle()`, after a confirmation for archive | No row → `adventure_unavailable`. |
| Add, rename, tick, delete objective | Single-row `insert` / `update` / `delete` with `.select()` | No row → `adventure_unavailable`, refetch. |
| Post, delete update | Single-row `insert` / `delete` with `.select()` | Same. |

### 4.2 Concurrency

| Race | Outcome |
| --- | --- |
| Two members save details of the same main adventure from the same version | The first wins. The second gets `adventure_conflict` with their text kept (D11). |
| A status change while someone edits details | The status write advances `updated_at`, so the details save conflicts and shows the banner. Correct: the row changed. |
| Two members tick the same objective | Both succeed; the row ends ticked by the later one. |
| Five parallel objective inserts at 49 | Exactly one succeeds. The same holds for updates at 499 and adventures at 199. |
| The creator archives while someone edits | The other save matches no row and the re-read finds nothing → `adventure_unavailable`, text kept. |
| A character is deleted while `create_adventure` runs for it | The character lock serializes them: either the create fails with `adventure_character_unavailable`, or the delete removes the new adventure (D5). |
| `create_adventure` while the creator is removed | The campaign lock serializes them: either the create fails with `adventure_campaign_unavailable`, or the adventure is created and then hidden. |

Invariants after any interleaving (asserted by tests): no personal or side adventure without an accepted participant, no main adventure with participants, no participant whose character is in another campaign or owned by another player, and no cap exceeded.

| Message | Copy |
| --- | --- |
| `adventure_conflict` | "This adventure changed while you were editing. Your text is still here." With **Load latest** and **Save mine anyway**. |
| `adventure_unavailable` | "This adventure is no longer available. It may have been archived." |
| `adventure_archived` | "This adventure is archived. Restore it to make changes." |
| `adventure_limit_reached` | "You can keep up to 200 adventures in a campaign, archived ones included." |
| `adventure_objective_limit_reached` | "An adventure can have up to 50 objectives." |
| `adventure_update_limit_reached` | "This adventure has reached 500 updates." |
| `adventure_character_unavailable`, `adventure_character_required` | "Choose one of your characters in this campaign." |

| `adventure_type_change_forbidden`, `adventure_reassignment_forbidden`, `adventure_archive_creator_only`, `adventure_main_has_no_participants` | Fallback (the UI never offers these) |

## 8. Non-destructive migration strategy

### 8.1 Files (timestamp after `20261116110500`; use the real creation time)

| # | File | Contents |
| --- | --- | --- |
| 1 | `2026111?xxxxxx_add_adventures.sql` | The four tables, constraints, indexes, both helpers, the guard, cap, and orphan triggers, `create_adventure`, RLS, revokes, grants, and policies. |

Wrapped in `begin; … commit;`. It changes no existing table, policy, grant, function, or trigger. No backfill.

### 8.2 Pre-flight (read-only)

1. `git status` is clean, or contains M5 changes only.
2. `npm run supabase:status`. `schema_migrations` lists exactly the 24 versions ending `20261116110500`.
3. Baseline in a read-only transaction: row counts of every existing `public` table, and the M1 ownership-consistency query (0 rows).
4. Optional local safety net outside the repo: `pg_dump --data-only` of `public` and `auth` to the scratchpad.
5. Baseline suites: `npm run lint`, `npm run format:check`, `npm run build`, `npm test`, `npm run test:local-supabase`. `test:e2e` is not run (your preference).

### 8.3 Apply

`npm run db:migrate` (from `implementation/backend`), then `npm run db:types` and `npx prettier --write src/types/database.ts`. Never `db:reset`.

### 8.4 Post-migration checks (read-only)

| Check | Expected |
| --- | --- |
| Existing row counts | Identical to baseline (profiles may rise only from test accounts) |
| `relrowsecurity` on the four tables | true |
| Table and column privileges | Exactly §3.1 for `authenticated`. Nothing for `anon`, `service_role`, or `public`. |
| Function privileges | Both helpers and `create_adventure`: `authenticated` and `postgres`. Guards and the orphan trigger: `postgres` only. |
| Existing ACLs and the departure hook | Unchanged |

### 8.5 Rollback (compensating migration only)

Drop the four tables and the new functions. **This deletes every adventure.** Acceptable only before real use; otherwise export first.

### 8.6 Test-data safety

Integration tests create their own accounts and campaigns and delete their campaigns in `finally`. Counts are scoped to the test's own campaigns. Direct `postgres` writes run inside `begin; … rollback;` through `localDatabaseQuery`.

## 11. Acceptance criteria (M5 as a whole)

1. A member can create a personal, side, or main adventure at the map table, edit it, change its status, complete and reopen it, manage objectives and updates, and the changes persist across a reload.
2. A personal or side adventure, with its participants, objectives, and updates, is readable only by its participant while they are a member. The campaign owner has no override, and no list, count, or embed reveals it.
3. Every current member can read and edit a main adventure. Only its creator archives or restores it.
4. Two people saving the same details from the same version never overwrite each other silently.
5. No one can create an adventure for another player's character, move rows between campaigns or creators, change a type to or from main, edit an archived adventure, or exceed a cap.
6. Leaving or removal changes no rows; rejoining restores access. Deleting a character removes the adventures only it was in, after a confirmation that says so.
7. Deleting a campaign removes its adventures after a confirmation that says so.
8. Existing behaviour and its tests are unchanged.
9. The migration ran with `db:migrate` only, existing counts are unchanged, no `db:reset` was run, and every §9.4 command run is reported.

## 12. Risks and edge cases

### Risks

| Risk | Mitigation |
| --- | --- |
| The visibility helper is wrong and leaks a private adventure | It is the single source for every policy. Tests check every table and embed for the owner and for another member. |
| Without Realtime, members see main-adventure edits only on refetch | Refetch on focus and on opening; the conflict flow prevents lost text. Realtime is M7. |
| D5 deletes a player's adventures with their character | The confirmation gives the count. Retiring a character keeps them. |
| A departed creator's main adventure can never be archived (D4) | Members can still edit or complete it. D4's alternative is a small follow-up. |
| M6 needs to change visibility, which the M5 guard forbids | M6 replaces the guard in its own migration and routes visibility through RPCs, as M03 §3 planned. |
| A sixth plate crowds the right of the scene | Phase 3 checks plates at 390 px with a targeted capture and moves one below if needed. |
| The client's bounds drift from the database checks | One source of limits in `adventureValidation.ts`, mirrored by the SQL; integration tests send every boundary. |

### Edge cases covered

- An adventure can be only a title; every other field is optional.
- A character retired or marked deceased keeps its adventures.
- A player with several characters chooses one per adventure; their other characters gain nothing.
- An adventure open in the editor is archived elsewhere → `adventure_unavailable` for others, text kept, list refreshed.
- A double-submitted create makes two adventures; the button is disabled while pending.

- **M7**: Realtime for main-adventure edits and objective ticks.
- **M8**: `adventure_handoffs` attaches through `adventures (id, campaign_id)`, already unique.
