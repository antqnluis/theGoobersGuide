### Deviations from the plan

1. **Weight above the bound reports `22003`, not `23514`.** Plan §9.1 expects weight 100,000 to fail with `23514`. The column is `numeric(7, 2)`, which cannot hold 100,000 at all, so PostgreSQL raises `numeric field overflow` (`22003`) before the check runs. The bound is enforced either way (99,999.99 is accepted, 100,000 and 99,999.999 are refused); `character_items_weight_check` still covers negatives. The tests assert `22003` for the upper bound. Frontend validation (Phase 3) enforces 0–99,999.99 with field messages, so users never see this code.
2. **Test-data safety.** The first draft of the currency-check test updated `character_sheets` without a `where`, which touched the real sheet inside a rolled-back transaction. It is now scoped to the fixture character, and the real sheet was verified unchanged afterwards.
3. **Migration timestamp** is the real creation time (`20261114190000`); the plan's `…160000` was illustrative.
4. `src/types/database.ts` is not regenerated yet. That is Phase 3.

### Deviations from the plan

1. **Membership is re-checked after the campaign lock, in its own statement.** Plan §4.1 step 3 locks the campaign `for share` "where the caller is a current member". With the membership test inside the locking statement, a removal that commits while the call waits for the lock would still be seen as a member (the statement's snapshot predates the removal). ## Change request — spending makes change (2026-11-14) — done

D5 amended at the user's request: spending a coin you do not have (for example 5 sp with only gold) no longer fails; it breaks a larger coin and returns the change in smaller coins (10 cp = 1 sp, 10 sp = 1 gp). Adding coins is unchanged.

How: `planSpend(purse, amounts)` in `inventoryRules.ts` returns the balance changes, or null when the whole purse is worth less than the cost. It pays with the coins asked for first, then smaller coins that fit, and only then breaks one larger coin, giving change in the largest smaller coins that fit (so 5 sp from 3 gp becomes gp −1, sp +5). `CharacterCoins` sends those changes through the existing `adjust_character_currency`, so the payment and the change are one atomic, all-or-nothing call and there is no migration or RPC change. If the purse cannot cover the cost, the plain amounts are sent and the database refuses them with its usual message, so an out-of-date purse can never overspend. The notice names the change: "Spent 5 sp (made change from 1 gp)."

Tests: `planSpend` unit tests (exact coins, gold to silver, gold to copper, silver to copper, smaller coins for a larger one, requested coin first, refusal) plus an exhaustive property check (no negative balance, total value conserved, null exactly when unaffordable); `CharacterCoins` tests; the mocked browser overspend test now overspends the real total, and a new browser test covers making change.
